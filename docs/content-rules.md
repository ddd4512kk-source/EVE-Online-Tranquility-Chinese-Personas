# 内容规则

由 [AGENTS.md](../AGENTS.md) 指定的内容规则。各节按任务加载；文中代码路径均相对仓库根目录。收录与归因以本页为准，字段示例看模板，写作展开与验收看 [writing-review.md](writing-review.md)。

## 2. 总方针：宁收勿漏，有线索就发挥

这是本站最重要的规则，其他规则与它冲突时以它为准。

- **立传门槛很低**：有一件有出处、足以体现本人社区经历的独立事件 + 能对上一个角色，就写。帖子、回忆、截图和视频评论区是来源形式，不因有一条发言就自动达到立传门槛。料少写短篇，不等料齐；以后有料再补。**但只有一条料且分量不重时，必须先补料**：至少跑完游戏画像（简介全文、简介挂的 KM 逐张点开、综合 KB、高值月份代表 KM 对照战役表），再追具体事件；补不到就留 `docs/leads/`，暂不列入群像。职务头衔本身不算料。CEO、联盟重要管理者与FC不受此条约束，见下条。大事件的主角即使只有一个来源，也直接写；**重大黑料的主角，即使只有这一件事，也必须立传**，不要放进线索等人决定。
- **候选与列传分开，CEO、联盟重要管理者与FC可以留短篇**：月榜、累计 KB、参战名单、战果签名、KB 分析、简介自嘲和普通聊天只是找人入口，单独或拼凑都不够立传；普通成员须有具体社区事件、争议、行为影响或其他独立故事，本人教学、持续创作及作品互动也算。有任职依据的军团 CEO、联盟重要管理者（盟主、联盟执行／核心管理、联盟总监、联盟外交或战争负责人等联盟层级的实际工作，不限头衔；本人任一号在联盟执行军团，即算联盟高层），以及有指挥依据的 FC，故事暂少也可留短篇，不受上一条单料门槛约束，不因故事少撤回。**这里的管理只指联盟管理**：军团内部的总监、人事、招新、物流、外交等管理岗按普通成员算，适用上一条。未达门槛者留在 `docs/leads/` 继续取材，行数不作去留标准；细则见[写作验收](writing-review.md#成稿验收)。
- **角色对应不必等本人确认**：本人自报、帖中署名、截图里的角色名、同名且军团或时间吻合，都算依据，记进素材文件即可。一人多号在 EVE 极常见：名字极相近（同词根加数字或字母、大小写或形近字替换、同头衔）且同军团或同联盟的角色，直接判为本人小号，不写“未证实同人”；收录号选主号或最有故事的号，其余号名写进 `aliases`，角色 ID 写进 `alts`（战役战报据此认人），依据记素材。完全找不到角色时才进备忘录 [docs/pending-characters.md](pending-characters.md)。
- **先核服务器归属**：eve 吧大部分内容来自国服，对本站属于低质量、低优先级线索来源，不作默认补查入口。先对上宁静服人物与社区交集，再决定入料；同名、跨服同名组织和中文角色名不证明欧服归属。明确为国服且无独立欧服交集的事件，撤出待收录队列，保留排除记录；服务器不明的先标待核，不套给欧服角色。已对应欧服人物的国服旧事另记同人依据，正文点明发生在国服。具体方法见 `docs/research-method.md`。
- **跨平台账号顺着本人发言认**：已对应到本人的贴吧等账号，用第一人称讲自己的一件事，并直接贴出同一事件的 B 站视频、动态或主页；UP 名又与其外号同名、拆字、谐音或惯用变体相合，就直接归为本人账号，写进 `aliases` 和素材，不再等视频口播自报或第二个独立来源。把“本人叙事 → 本人贴链接 → 平台作者名”的链条记清。单有近似昵称、单纯转发别人的作品，继续按内容与上下文核对。
- **料不足就发挥，这是写作要求，而且要显著发挥**：“不足”指细节不足，不是分量不足。料本身要够重（有冲突、有名场面、有圈内议论、有黑历史），只是只剩线索和骨架，才发挥补血肉；料本身客观上轻（日常的一张 KM、一晚普通行动、普通换团参战、无关痛痒的闲聊），就放弃这条料，不靠发挥把它吹大。在够重的料上，主动顺着人物处境、利益冲突和言行反差推测动机、串起前因后果，写出戏剧性，允许夸张、反讽。料少不等于块短：来源哪怕只有一句话，也要展开成一段完整的小故事，一般四五句以上。推测和想象用肯定的口气直接写，不加“大概”“想来”“看样子”，更不逐句自我否定。不能只摘录事实再贴一句笑话，也不能把“骨架不能编”扩大成“只能复述原帖”。
- **指控没被证伪就照写**：社区爆料、单方说法、对手宣传都能用，当故事直接讲，不加“据传”“据某某爆料”“圈内一说”；出处放链接和素材。不需要查证，不等当事人认账，正文不堆免责声明、不写考据过程。
- **唯一的硬约束：骨架不能编。** 事件、当事人、时间、战果和当作本人原话引用的话要有出处；心理、动机、场面和想象的台词属于发挥，不受此限，边界见[写作验收·发挥边界](writing-review.md#发挥边界)。已被证伪的不写，或写成“谣言被戳穿”。
- **素材全留，正文按分量组织**：有出处的料完整归档，重要事件充分入文。黑料超过 20 块时，按[写作验收](writing-review.md#黑料过多时合并与取舍)复核：同一事件合并，低严重度轻料可只留素材，不为凑数拆块，也不为压数删重事。模板里的一红两黑只是格式示例。此人以什么出名，那件事就是最重的一块。战斗记录按第 3 节“战绩红料写总结性点评”归纳，不要求逐条入文。B站作品推荐按下一条精选规则处理；未入选作品中的具体事迹、言论和红黑料仍照常归档，入文按上述分量与合并规则处理。
- **B站 UP 作品精选**：先读本人空间，分别查“最新发布”和“最多播放”，再结合合集／系列选候选；不得只看最新首页就代替频道调查。已确认的UP身份不因作品未读完或精选未完成而撤掉。人物是 B站 UP 时，从其本人作品中挑选最多5个比较优秀的作品放进列传，附作品标题、公开链接和简短推荐理由。联合制作的视频不作为作者本人的推荐视频，不计入这最多5个精选名额。依据实际读到或看过的内容，优先选有鲜明个人特色、精彩叙事、实用讲解或出色制作的作品，不只按播放量或标题挑选。若前两个候选质量较高，应继续扩大候选并补足5个，不能选到2个便以“最多5个”为由收尾。只有继续筛选后确实不足5个合适作品时才少选，并在素材记明筛选范围、未入选原因及未读缺口；不能把未读当作质量不够，也不把平庸视频硬塞进来。
- **素材先留存，再决定是否入文**：搜索和接收素材时，尽量保留原始内容及必要上下文、出处、时间、作者/说话者和角色对应线索。暂时不适合写入正文、暂时无法归属或暂时看不出用途的材料，也要归档并标注待核问题或暂缓原因，供以后补写、复核和重新判断；不要因为当前用不上就丢弃。归档仍须遵守现实隐私禁区。

## 3. 红料与黑料

- **黑料** = 此人自己的言行带来的难堪：吵架、滥权、食言、坑人、awox、指挥翻车、自相矛盾、自吹、错字。
- **军团料，CEO 负责**：军团在某人任 CEO（或同级主事者）期间集体干出的黑料（滥刷、不讲规矩、名声烂、被联盟收拾），算这位 CEO 的黑料，不要求证明他本人下场。点明“某某军团治下”“其任内”，只算任职期内，成员的个人私事不算。军团的普通胜负、被打败仍不算黑料。
- **不算黑料**：普通胜负、普通丢船、KB 低、换团换盟、去对面阵营、联盟解散。可作背景，有故事才写。“几年换几家军团”直接不写。
- **0 伤害显示不作讨论素材**：游戏存在伤害显示 bug，显示 0 伤害不代表实际没有造成伤害。不得据此评价人物的输出、贡献、能力或参战态度，也不作为红黑料、笑点或讨论内容；即使来源拿它起哄，也不沿用这一论据。参战按名单、舰船与其他已有依据叙述。
- **高价值旗舰战果**：泰坦、超旗的击杀或损失可以入料（击杀算红、损失算黑），只写战果，不推断责任。这是料的归类，不是独立立传的例外；仅参与一次或多次旗舰击杀、再加 KB 分析，仍需独立人物事件或 CEO／联盟重要管理者的职责或FC指挥依据支撑列传，不能用简介自嘲或普通闲聊补足门槛。没有这些的先保留战果素材。
- **战役分档**：旗舰战／超旗战按各方总损失，**100B–不足 400B 为中型，400B–不足 1T 为大型，1T 及以上为史诗**。相关人物的参战关联由战役互链列举；列传正文按下一条作总结性点评，不按分档逐场复述。
- **战绩红料写总结性点评**：综合 zKB／KB 与战役经历，写出此人的战斗风格、长期角色、经历变化及其在阵营里的分量，评价须落在已有记录上。参战清单已有互链，正文不再列全战役，不按日期逐场报星系、舰船、击杀和损失，也不逐张列 KB、逐项念累计数字。只展开能体现人物特点、转折、冲突或反差的代表战斗，数字与 KM 链接仅在支撑具体情节或判断时保留；其余记录归素材与战役页。综合 KB 评价不能被几场大仗的名单替代，独立人物事件、重要指挥经历与红黑料也不能借精简之名删掉。具体写法与验收见[写作验收](writing-review.md#zkb与战役写点评不写账本)。
- **小号参战**：战斗叙事以自然人为主语，主号与小号按事件合并，不分号写履历；角色 ID 和逐号统计留在素材，正文仅在故事需要时提号名。本人小号参战也算本人经历；优先查 KB 参与击杀价值达 100B 的主力号，低于此值可略过，已有参战证据照收。各号统计不直接相加。
- **监视者 = 在指挥位**：开 Monitor（监视者）进战场就是在指挥，开过数十次以上的是重要 FC；华人阵营里未对上收录人物的驾驶员，按[取材手册](research-method.md#七监视者驾驶员反查)反查备案。正文直接当 FC 写其带过的仗、局势与处境，不提船型、不念次数；监视者 KM 数只用来判断指挥分量，不换算成带出的击杀。写法见[写作验收](writing-review.md#开监视者的就写他在指挥)。
- **指挥依据**：本人自称FC或记述自己带队、他人明确称其为FC或佐证其指挥经历、公开指挥职务、动员／复盘，以及驾驶Monitor参战，均可作为FC收录依据，不要求必须有Monitor记录。只有概括身份时，不补造具体战役名与战果，但可以顺着身份推演其带队日常与风格。zKB自动FC标签仅为调查线索，不代替本人或社区依据。
- KB 累计按其统计范围表述，不把集体战果独算个人功劳。
- **不替当事人体面化**：社区黑话照写，强暴就写强暴。
- **立场中立**：写整个华人社区，不站 FRT 或任何一方。打赢 FRT 是战绩，不是黑料。
- **被盗号的人是受害者**，不当黑料；指控别人盗号、诈骗等现实违法行为，需要有翔实证据。

## 4. 文风

- 戏谑、损而不恶，像熟人互相揭短：读者笑出声，当事人只能苦笑。白话为主，可点缀史书笔法（“时人谓之……”）和社区黑话。
- 先讲故事：开篇一两段交代此人是谁、在哪混、和谁发生了什么。游戏数据只在服务主线时出现，不堆档案。
- 笑点长在事实后面：先摆事，再一两句损。数字只说它统计的事（KM 上有名字只说明参与了）。
- **口吻不保守**：这是野史，用说书人的口气直接讲。不加“据传”“据某某爆料”“帖主称”“圈内说”“想来”“大概”“看样子”一类护身词，出处放链接和素材。写法见[写作验收](writing-review.md#从素材到正文)。
- **正文讲人和事，核查账留素材**：待核名单、人数缺口、来源完整度与归因限制写进 `materials-*.md`。禁止作者用“尚无法确认”“不能证明”“帖里没交代齐”“具体责任不明”等话收尾。来源互相反驳时直接写双方怎么说；确实影响情节理解的分歧融进叙事，不列研究问题。
- **不确定细节就换写法，别给整段踩刹车**：人数只有估计就写“百来号人”；不知道谁下令就围绕已被点名的人和冲突写，不补造发令者。动机、心理与场面放手推演，骨架照[发挥边界](writing-review.md#发挥边界)。KB 用“参与”，自吹用“他自称”，不先夸大再补一句“这不能证明”。
- **文风也要验收**：写作前读 [写作验收与改写例](writing-review.md)，成稿按其中标准通读。素材缺口罗列、来源辩护或消毒式结尾算未完成；仅删掉免责句仍不够，要把线索展开成人物故事与锐评。
- `epithet` 一句话，≤25 字，要狠；`::: 评` 一两段。
- 中文要地道，不要翻译腔。术语按 [docs/glossary.md](glossary.md)；表里没有的词保留原词，不自造译名。
- 截图、私聊、群聊来的料直接写事，不描述截图、群名、时间。有网址的公开帖附链接。
- **禁区**：现实隐私（真名、单位、住址、电话、照片）；地域、民族、性别、外貌歧视；未成年人不收；游戏世界观与 NPC 势力（种族、NPC 学校、NPC 军团）不写，进出 NPC 军团只说“换军团”“退团”。

## 5. 文件格式

### 目录

每人一个目录 `src/people/<短名>/`（小写字母、数字、连字符）：

- `<短名>.md`：列传；`materials-<短名>.md`：素材与来源（不生成页面）；
- `<ID>.json`、`portrait-<ID>.jpg`：抓取的快照，勿手改。
- 以 `_` 开头的文件被忽略。模板见 [docs/person-template.md](person-template.md)。

### front matter（只允许这 6 个字段，多写或拼错会构建失败）

```yaml
---
character_id: 2000000000   # 必填，收录角色 ID
cn_name: 某某               # 可选，社区中文名，作为标题
aliases: [外号甲, 外号乙]   # 可选，外号，可被搜索
epithet: 一句话锐评          # 强烈建议
tags: [00区, 工业]          # 可选
alts: [2114818738]         # 可选，本人小号的角色 ID，战役战报据此认人
---
```

- 不手写角色名、创号时间、军团等游戏数据，由脚本提供。
- `tags` 的取舍、身份标签与军团／联盟 ticker 规则见[写作验收](writing-review.md#标签)；`npm run check`、`npm run build` 会校验军团与联盟标签。

### 正文

```markdown
开篇叙事。

::: 红料 标题
……
:::

::: 黑料 标题
……
:::

::: 评
文末锐评。
:::
```

- 每个独立事件一块，同一事件的后续合并叙述；块不能嵌套，以单独一行 `:::` 结束。一般先红后黑。
- 单个换行即换行；聊天记录用 `> 某某 > 这船怎么又炸了`，每行一句。
- 不用 `#` 一级标题。
- 提到已有列传的人加互链，写相对路径 `[名字](../<角色ID>/)`，不要以 `/` 开头。
- 术语蓝字由构建自动生成，来源是 `docs/glossary.md`；同形多义词（F1、T2、KOS、EFT 等）按语境处理，不全局替换。

### 战役

- **先判定是否为战役，再按损失分档**：少数旗舰出事、双方人数悬殊且不成比例的单方面围猎或转移事故，不收为战役；不能仅因昂贵舰船把总损失推过100B就立页。这类事件保留在相关人物列传与素材中。例：2023-10-17 HED-GP代驾事故。

- **相关视频**：战役页可在正文后介绍最多 6 个与本场直接相关的 B站视频，每条附标题、UP 主、公开链接和简短介绍。优先补充不同阵营、视角或复盘内容，同一 BV 不重复，不凑满名额；无合适作品时不显示空节。战役推荐不套用人物本人作品精选限制，联合制作、官方或他人视角均可，按公开署名说明，不把投稿者等同于唯一作者。依据实际读取内容介绍；只读公开文字时，不声称看过影像或评价剪辑、画面、音轨。对应本场的依据、阅读范围与待补候选归本场素材。字段格式只在战役模板维护。

- **星系名用中文**：战役标题出现低安星系名时，必须使用游戏内中文名或已有通行中文名；先查 `src/_data/systemNames.js`，缺名时查 CCP ESI 中文资料并补入，不能直接沿用英文标题或自行音译。正文、人物列传中的战役链接文字同步使用中文；`systems`、路径、英文别名和来源原题保留英文。00 区字母数字星系名照原名。

- 一场一篇：`src/battles/<短名>/<短名>.md`，素材 `materials-<短名>.md`。同一星系先后几场按单场时间窗口分开写；但几天内接连打的同一轮攻防，单场不足门槛或分量偏轻的，编为一场（如 Y-MPWL 2025-08-19—08-25）：`start`／`end` 覆盖全程，总损失为各场之和，`loss_source` 列各场战报。已编进一组的单场不另立页；同一星系日期重叠的两页构建失败。
- `tags` 供目录筛选（地带、战型、主要势力），规模档位自动加。联盟标签用联盟游戏内 ticker（同列传，如 FRT、CONDI、INIT.），不用俗称；`sides`、`corps` 里的联盟、军团名写游戏内全名（大小写、句点照抄）。
- **联盟、军团写 ID**：front matter 里的联盟（`sides[].alliances`，无联盟的军团写军团 ID）和手填军团都只写 ID，名字由全站名称表 `src/_data/entityNames.json` 提供；ID 用 `npm run find -- "全名"` 查，表里没有的由 `npm run fetch` 向 ESI 补。**华人军团**在名称表里给该军团加 `"chinese": true`，全站所有快照战役据此自动列出、计人数；非华人军团（如 GoonWaffe）里有华人成员也不标。
- 按各方总损失（单位 B）自动分档：100B–不足 400B 为**中型**，400B–不足 1T 为**大型**，1T 及以上为**史诗**；不足 100B 构建失败。总损失必须附来源 `loss_source`。
- **快照战役（首选）**：`loss_source` 全是 br.evetools 或 killmail.app 完整战报时，`npm run fetch`／`build` 抓战报精简存成同目录 `br.json`（勿手改），全场与各方的人数、损失、记录条数，华人军团人数和参战的已收录人物（收录号与列传 `alts` 小号）都由它算，front matter 不写数字，也不手列 `people`。`sides` 记 2–4 方的阵营名与点名联盟，华人军团按名称表标记自动算，不手列；战报跨场时用 `window` 截时段。战报作者分的队伍按点名联盟整队归方，没分队或分队与点名冲突时按交火推断，归不了方的自动并成“第三方”。人物页按算出的人物自动显示“战役”反链；人物的个人战绩按第 3 节作总结性点评，正文不重复参战清单。
- **小规模第三方不展示**：全站所有战役中，第三方合计参战不足 30 人时，目录与详情页均不单独显示其阵营、人数、损失、军团或人物，不另写第三方正文段落，也不计入页面显示的交战方数量。原始记录、全场总人数与总损失及人物战役关联照常保留；第三方达到 30 人或人数未知时仍显示。
- **手填战役**：来源有 CCP 新闻、WarBeacon、EVE-KILL、论坛自报等别的口径时，`total_loss` 和各方参战角色数（`pilots`）、损失金额（`loss`，B）、损失记录条数（`loss_count`）照来源手填，`corps`（每项 `{ id, pilots }`）、`people` 写在各方下。分方三项必须显式填写，全场总数不能替代；确实取不到才写 `null` 并以 `stats_note` 记来源缺口和续查入口，页面显示“待补”，不得省略或填 0。0 仅表示来源确认没有损失。人数按角色去重，损失按受害方计，记录条数可含胶囊与建筑，不冒称纯船体数；窗口、星系、阵营映射与差异留素材。
- 正文按阵营分节，写各方的华人人物与华人军团。人物列传引用已有战役页时链到 `../../battles/<短名>/`，KM 链接照留。
- 字段、正文结构与互链写法见[战役模板](battle-template.md)，流程用 `add-battle`；文风与红黑料规则同列传。

## 6. 素材归档

- **默认以 Markdown 总结精炼素材**：外部图片、聊天记录、PDF 和其他文件可能随时消失，读懂后把事件经过、关键原话、必要上下文、人物对应、出处和待核问题融入人物素材；不依赖原文件长期存在。不要全文转录、堆聊天流水账、保存文件名／哈希／原排版，或重复记录处理过程。分清事实、来源方说法与推测，关键内容读不清的标出缺口，不补造。
- **少存二进制文件**：不批量备份图片或 PDF；只有文字无法替代的关键图才少量保留，并去除现实隐私。能用文字完整消化的，不再保存原图原件。
- 已收录人物的来源与检索记录 → 本人目录 `materials-<短名>.md`。
- 未收录或角色对不上的人 → `docs/leads/<短名>.md`，并在 [docs/pending-characters.md](pending-characters.md) 登记一行。收录后移入人物目录。
- [docs/materials.md](materials.md) 只作索引，写完列传同步状态。
- **清单须有续查用途**：未完成调查的固定队列、阅读覆盖、失败与排除记录保留；已经完成的写作、消化、验收报告不另作长期全员清单。独有事实和来源先归入本人素材或共享事件，未完成事项归线索与备忘录，再删除重复报告；同一队列只维护一份状态表，索引直接指向正式归档，不新建层层转跳的列表。
- 材料只写事实、说法和来源，不记录素材提供者身份或对话过程，不写“维护者确认”。
- 搜索或接收材料时尽量保存原文/关键内容与上下文、来源和待核问题；暂时不能写入正文的也归档，标注暂缓原因或后续核对条件，不因暂时无用而删除。不得为留存素材而保存现实隐私。
