# 内容规则

由 [AGENTS.md](../AGENTS.md) 指定的内容规则，各节按任务加载；代码路径相对仓库根目录。收录与归因以本页为准，字段示例看模板，写作展开与验收看 [writing-review.md](writing-review.md)。

## 2. 总方针：宁收勿漏，有线索就发挥

这是本站最重要的规则，其他规则与它冲突时以它为准。

- **立传门槛很低**：一件有出处、能体现本人社区经历的独立事件，加上能对上的角色，就写；料少写短篇，以后再补。帖子、回忆、截图和评论区只是来源形式，有一条发言不等于够门槛。**只有一条轻料时先补料**：先读简介全文和 stats 总览，再追具体事件；船型细目、月份与 KM 按[游戏画像](research-method.md#1-游戏画像定位人物时按需)中的实际问题选查，不作为统一必查清单。补不到独立故事则留 `docs/leads/`。职务头衔本身不算料。大事件主角即使只有一个来源也直接写；**重大黑料的主角，哪怕只有这一件事，也必须立传**，不放进线索等人决定。
- **找人入口不等于立传依据**：月榜、累计 KB、参战名单、战果签名（含泰坦／超旗）、KB 分析、简介自嘲和普通聊天，单独或拼凑都不够；普通成员须有具体社区事件、争议、行为影响或其他独立故事，本人教学、持续创作及作品互动也算。**例外**：有任职依据的军团 CEO、联盟重要管理者（盟主、联盟执行／核心管理、联盟总监、联盟外交或战争负责人等联盟层级实际工作，不限头衔；本人任一号在联盟执行军团即算），以及有指挥依据（见第 3 节）的 FC，故事少也可留短篇，不受单料门槛约束，不因故事少撤回。军团内部的总监、人事、招新、物流、外交等岗位按普通成员算。未达门槛者留 `docs/leads/` 继续取材，行数不作去留标准；细则见[写作验收](writing-review.md#成稿验收)。
- **角色对应不必等本人确认**：本人自报、帖中署名、截图里的角色名、同名且军团或时间吻合，都算依据，记进素材。名字极相近（同词根加数字或字母、大小写或形近字替换、同头衔）且同军团或同联盟的，直接判为本人小号，不写“未证实同人”。收录号选主号或最有故事的号；其余号的 ID、正式名字与依据写进本人 `<ID>-id.json` 的 `identity.alts`，别称写 `person.aliases`（战役战报据此认人）。完全找不到角色才进备忘录 [docs/pending-characters.md](pending-characters.md)。
- **先核服务器归属**：eve 吧多为国服内容，只是低优先级线索，不作默认补查入口。**EVE 手游吧内容不追查**：搜索、互链或旧队列命中后标【手游吧排除】，只留简短排除记录，不继续追正文、作者或回复网络，不作为宁静服人物与事件的取材依据。同名人物、跨服同名组织和中文角色名都不证明欧服归属。明确国服且无独立欧服交集的事件撤出待收录队列并留排除记录；服务器不明的标待核，不套给欧服角色；已对应欧服人物的国服旧事另记同人依据，正文点明发生在国服。方法见[取材手册](research-method.md)贴吧节。
- **跨平台账号顺着本人发言认**：已对应本人的贴吧等账号用第一人称讲自己的事，并贴出同一事件的 B 站视频、动态或主页，UP 名又与其外号同名、拆字、谐音或惯用变体相合，就直接归为本人账号，写进身份档案（见[人物身份数据](person-identity.md)），外号可写 `aliases`；素材记清“本人叙事 → 本人贴链接 → 平台作者名”的链条，不再等口播自报或第二来源。只有近似昵称或单纯转发他人作品的，继续按内容与上下文核对。
- **料不足就显著发挥**：“不足”指细节不足，不是分量不足。料要够重（冲突、名场面、圈内议论、黑历史），只剩骨架时，就顺着人物处境、利益冲突和言行反差推测动机、串起前因后果，写出戏剧性，允许夸张、反讽；客观上轻的料（日常一张 KM、一晚普通行动、普通换团参战、无关痛痒的闲聊）直接放弃，不靠发挥吹大。来源哪怕只有一句话，也展开成一般四五句以上的完整小故事；不能只摘事实再贴一句笑话，也不能把“骨架不能编”扩大成“只能复述原帖”。口吻按第 4 节。
- **指控没被证伪就照写**：社区爆料、单方说法、对手宣传都当故事直接讲，出处放链接和素材；不查证、不等当事人认账，正文不写免责声明和考据过程。
- **唯一的硬约束：骨架不能编。** 事件、当事人、时间、战果和当作本人原话引用的话要有出处；心理、动机、场面和想象的台词属于发挥，不受此限，边界见[写作验收·发挥边界](writing-review.md#发挥边界)。已被证伪的不写，或写成“谣言被戳穿”。
- **素材全留，正文按分量组织**：有出处的料完整归档（见第 6 节），重要事件充分入文；此人以什么出名，那件事就是最重的一块。模板里的一红两黑只是格式示例。黑料超过 20 块时按[写作验收](writing-review.md#黑料过多时合并与取舍)复核：同一事件合并，低严重度轻料可只留素材，不为凑数拆块，也不为压数删重事。战斗记录按第 3 节“战绩红料写总结性点评”归纳；未入选精选的 B站作品，其事迹、言论与红黑料照常归档和入文。
- **B站 UP 作品精选**：人物是 B站 UP 时，从本人频道挑最多 5 个优秀作品放进列传，附标题、公开链接和基于实际读到内容的简短推荐理由。
  - 候选：先读本人空间，分别查“最新发布”和“最多播放”，再看合集／系列，不能只看最新首页。优先鲜明个人特色、精彩叙事、实用讲解或出色制作，不只按播放量或标题挑。
  - 可选范围：翻译、搬运可入选，写明本人承担的翻译、转载或整理，按公开署名分清原作者与上传者，不冒称原创。联合制作不算本人推荐，不占名额。正文红料或黑料已展开的视频不重复推荐。
  - 数量：前两个候选质量较高就继续扩大候选，争取选足 5 个。因去掉正文重复而少选或不放可以；其他情形只有继续筛选后确实不足才少选。未读不等于质量不够，平庸视频不硬塞，没有精选时不显示空块。
  - 已确认的 UP 身份不因作品未读完或精选未完成而撤掉。

## 3. 红料与黑料

- **黑料** = 此人自己的言行带来的难堪：吵架、滥权、食言、坑人、awox、指挥翻车、自相矛盾、自吹、错字。
- **军团料，CEO 负责**：某人任 CEO（或同级主事者）期间，军团集体干出的黑料（滥刷、不讲规矩、名声烂、被联盟收拾）算他的黑料，不要求证明本人下场；写明“某某军团治下”“其任内”，只算任期内，成员个人私事不算。
- **不算黑料**：普通胜负、普通丢船、KB 低、换团换盟、去对面阵营、联盟解散，军团层面也一样。可作背景，有故事才写；“几年换几家军团”直接不写。
- **0 伤害不作素材**：KM 显示 0 伤害不代表没出力（显示 bug、后勤、拉点都常见），不拿它评价人或当笑点。
- **高价值旗舰战果**：泰坦、超旗的击杀算红料、损失算黑料，只写战果，不推断责任。这只是料的归类，不能单独撑起立传（见第 2 节），不够门槛时先留战果素材。
- **战绩红料写总结性点评**：有显著战斗经历的人，综合战绩单独写成一块红料，紧接开篇之后；不散在开篇、简介段或其他料块里代替。这块综合 zKB／KB 与战役经历，写此人的战斗风格、长期角色、经历变化和在阵营里的分量，评价落在已有记录上。参战清单已有战役互链，正文不列全战役，不逐场报星系、舰船、击杀和损失，不逐张列 KB、念累计数；只展开体现特点、转折、冲突或反差的代表战斗，数字和 KM 链接只在支撑情节或判断时保留，其余归素材与战役页。精简不能拿几场大仗名单代替综合 KB 评价，也不能删掉独立事件、重要指挥经历与红黑料。写法见[写作验收](writing-review.md#zkb与战役写点评不写账本)。
- **小号参战**：以自然人为主语，主号小号按事件合并叙述，不分号写履历；角色 ID 和逐号统计留素材，故事需要时才提号名，各号统计不相加。本人小号参战也是本人经历；查 KB 优先参与击杀价值达 100B 的主力号，低于此值可略过，已有参战证据照收。
- **监视者 = 在指挥位**：开 Monitor（监视者）进战场就是在指挥，开过数十次以上的是重要 FC。正文直接当 FC 写其带过的仗、局势与处境，不提船型、不念次数；KM 数只用来判断指挥分量，不换算成带出的击杀。华人阵营里未对上收录人物的驾驶员按[取材手册](research-method.md#七监视者驾驶员反查)反查备案；写法见[写作验收](writing-review.md#开监视者的就写他在指挥)。
- **指挥依据**：本人自称 FC 或记述自己带队、他人称其 FC 或佐证其指挥、公开指挥职务、动员／复盘、驾驶 Monitor 参战，任一即可，不要求必须有 Monitor 记录。只有概括身份时不补造具体战役与战果，可顺着身份推演带队日常与风格。zKB 自动 FC 标签只是调查线索。
- KB 累计按其统计范围表述，不把集体战果独算个人功劳。
- **不替当事人体面化**：社区黑话照写，强暴就写强暴。
- **立场中立**：写整个华人社区，不站 FRT 或任何一方。打赢 FRT 是战绩，不是黑料。
- **被盗号的人是受害者**，不当黑料；指控别人盗号、诈骗等现实违法行为，需要有翔实证据。

## 4. 文风

- 戏谑、损而不恶，像熟人互相揭短：读者笑出声，当事人只能苦笑。白话为主，可点缀史书笔法（“时人谓之……”）和社区黑话。
- 先讲故事：开篇一两段交代此人是谁、在哪混、和谁发生了什么。游戏数据只在服务主线时出现，不堆档案。
- 笑点长在事实后面：先摆事，再一两句损。数字只说它统计的事（KM 上有名字只说明参与了）。
- **口吻不保守**：这是野史，用说书人的口气直接讲，推测和想象也用肯定语气，不逐句自我否定。不加“据传”“据某某爆料”“帖主称”“圈内说”“想来”“大概”“看样子”一类护身词，出处放链接和素材。写法见[写作验收](writing-review.md#从素材到正文)。
- **正文讲人和事，核查账留素材**：待核名单、人数缺口、来源完整度与归因限制写进 `materials-*.md`，正文不用“尚无法确认”“不能证明”“帖里没交代齐”“具体责任不明”之类收尾。来源互相反驳就直接写双方怎么说；影响理解的分歧融进叙事，不列研究问题。
- **不确定细节就换写法，别给整段踩刹车**：人数只有估计就写“百来号人”；不知道谁下令就围绕已点名的人和冲突写，不补造发令者。KB 用“参与”，自吹用“他自称”，不先夸大再补一句“这不能证明”。
- **文风也要验收**：写作前读[写作验收与改写例](writing-review.md)，成稿按其标准通读。罗列素材缺口、为来源辩护、消毒式结尾都算未完成；只删免责句也不够，要把线索展开成人物故事与锐评。重料须另按[分量与发挥验收](writing-review.md#重料的分量与发挥验收)逐件审，战斗调查结论不能代替写作结论。
- `epithet` 一句话，≤25 字，要狠；`::: 评` 一两段。
- 中文要地道，不要翻译腔。术语用 `npm run glossary -- "词语"` 定向查询，遵守下方[术语用法](#术语用法)。
- **外文原话译成中文**：外文发言、帖子、评论在正文写中文译文，照原话的损劲儿译，不留整句外文。读者可能拿去搜的帖子标题、口号、绰号，译文后括注原文；人名、组织名、舰船名、术语按上一条。原文留素材。
- 截图、私聊、群聊来的料直接写事，不描述截图、群名、时间。有网址的公开帖附链接。
- **禁区**：现实隐私（真名、单位、住址、电话、照片）；地域、民族、性别、外貌歧视；未成年人不收；游戏世界观与 NPC 势力（种族、NPC 学校、NPC 军团）不写，进出 NPC 军团只说“换军团”“退团”。

### 术语用法

- [docs/glossary.json](glossary.json) 是术语、释义、确认状态和蓝字匹配配置的唯一来源，网站术语页、正文蓝字与弹窗由它生成。参数与字段用 `npm run glossary -- --help` 查看，不另抄词表。
- **已确认**的词按社区说法写；**待复核**的释义帮读者理解上下文，不强制据此改写正文。档案没有的词先保留原词，或按确有的正文用例补一条带上下文的待复核释义；不直译、机翻或猜造译名，不据此全站替换用语。
- 新词按对应英文字母顺序插入。同形多义词（F1、T2、KOS、EFT 等）按语境判断，不全局替换；船名兼作人物外号、普通词或组织名时保留具体语境。
- 舰船名沿 [CCP SDE](https://developers.eveonline.com/docs/guides/staticdata/) 中文名称写，正文优先中文，必要时补“级”；引用原文保留原词。格式迁移不改变译名或确认状态。
- 蓝字只标易卡住新读者且语义明确的词。确认状态、舰船类别、是否自动加蓝分别记录，不相互推定；匹配配置只改 JSON，不凭备注措辞猜规则。

## 5. 文件格式

### 目录

每人一个目录 `src/people/<短名>/`（小写字母、数字、连字符）：

- `<短名>.md`：列传；`materials-<短名>.md`：素材与来源（不生成页面）；
- `<ID>-id.json`：展示配置、游戏快照与人工身份共用的档案；游戏字段由抓取维护，展示配置写 `person`，人工关系写 `identity`，详见[人物身份数据](person-identity.md)。`portrait-<ID>.jpg` 为头像。
- 以 `_` 开头的文件被忽略。模板见 [docs/person-template.md](person-template.md)。

### 人物 JSON 配置

Markdown 只保留正文，不写 front matter。收录角色 ID 只在 `<ID>-id.json` 顶层 `id` 维护，并与文件名一致；中文名、别称、锐评和标签集中在 `person`。示例见[人物模板](person-template.md)，字段、小号与刷新规则见[人物身份数据](person-identity.md)。

- `aliases` 只放外号、简称和社区别称；小号是独立游戏角色，按 `identity.alts` 维护，不重复塞进别称。
- 角色名、创号时间、军团等游戏数据由脚本提供，不手写。
- `tags` 的取舍、身份标签与主要联盟 ticker 规则见[写作验收](writing-review.md#标签)；`npm run check`、`npm run build` 会校验组织标签。

### 正文

```markdown
开篇叙事。

::: 红料 标题
……
:::

::: 黑料 标题
……
:::

::: 评
文末锐评。
:::
```

- 每个独立事件一块，同一事件的后续合并叙述；块不能嵌套，以单独一行 `:::` 结束。一般先红后黑。
- 单个换行即换行；聊天记录用 `> 某某 > 这船怎么又炸了`，每行一句。
- 不用 `#` 一级标题。
- 提到已有列传的人加互链，写相对路径 `[名字](../<角色ID>/)`，不要以 `/` 开头。
- 术语蓝字由构建自动生成，见[术语用法](#术语用法)。

### 战役

- **先判是不是战役**：少数旗舰出事、人数悬殊的单方面围猎或转移事故不收为战役，不能靠昂贵舰船把总损失推过 100B 就立页，这类事件留在相关列传与素材（例：2023-10-17 HED-GP 代驾事故）。
- **规模分档**：按各方总损失（单位 B）自动分档，100B–不足 400B 为**中型**，400B–不足 1T 为**大型**，1T 及以上为**史诗**；不足 100B 构建失败。总损失必须附来源 `loss_source`。
- 一场一篇：`src/battles/<短名>/<短名>.md`，素材 `materials-<短名>.md`。同一星系先后几场按单场时间窗口分开写；几天内接连打的同一轮攻防，单场不足门槛或分量偏轻的编为一场（如 Y-MPWL 2025-08-19—08-25）：`start`／`end` 覆盖全程，总损失为各场之和，`loss_source` 列各场战报。已编进一组的单场不另立页；同一星系日期重叠的两页构建失败。
- **星系名用中文**：战役标题里的低安星系名用游戏内中文名或通行中文名，先查 `src/_data/systemNames.js`，缺名时查 CCP ESI 中文资料补入，不沿用英文或自行音译。正文和人物列传中的战役链接文字同步用中文；`systems`、路径、英文别名和来源原题保留英文。00 区字母数字星系名照原名。
- `tags` 供目录筛选（地带、战型、主要势力），规模档位自动加。联盟标签用游戏内 ticker（同列传，如 FRT、CONDI、INIT.），不用俗称；`sides`、`corps` 里的联盟、军团名写游戏内全名（大小写、句点照抄）。
- **联盟、军团写 ID**：同名战役 JSON 里 `battle.sides[].organizations` 的联盟／军团和手填军团只写 ID，名字由全站名称表 `src/_data/entityNames.json` 提供；ID 用 `npm run find -- "全名"` 查，表里没有的由 `npm run fetch` 向 ESI 补。**华人军团**在名称表里加 `"chinese": true`，全站快照战役据此自动列出、计人数；非华人军团（如 GoonWaffe）里有华人成员也不标。
- **先核完整分队，再写阵营**：实际打开 BR 网页，展开全部组织列表，记录组织 ID 及逐方人数、金额、损失条数，再与当事人复盘、逐舰记录和已确认的本场关系交叉核对。BR 会分错，默认分组不能盲从；原作者完整 BR 通常比自动 related 更能解释编组，但同样要核；API 缺 `teams` 不等于网页没分队，不能据此自行拆分联盟。来源冲突时逐项记差异与采用理由，已有明确依据的归属不因默认 BR 不同而被覆盖；未查清的留待核，不编换边或内讧。零散交叉命中、智能炸弹伤害、对多家组织开火、未归组余额和长期外交关系，都不能单独证明第三方。改分方须同步数字、人物与军团归属、正文和素材。
- **快照战役（首选）**：`loss_source` 全是 br.evetools 或 killmail.app 完整战报时，`npm run fetch`／`build` 把战报精简存进同名 JSON 的 `br`（勿手改）。人数、损失、记录条数、华人军团和参战的已收录人物都由快照算，不手填数字、`people` 或华人军团；`organizations` 是唯一的组织归方名单，`emblem` 只选主标，战报跨场时用 `window` 截时段。自动归方和联盟收纳只是后备，不替代上一条的人工核对；算法与展示门槛见[战役模板](battle-template.md#快照归方与统计)。
- **同一联盟不跨方**：同一场里同一联盟及其军团必须同方，跨方即归方错误：回查本场历史归属，修正组织映射、正文和素材，不解释为军团独立站队。归属取本场快照，不用军团当前联盟回填。联盟出现只说明有成员在场，不代表整体动员或统一指挥。附属联盟（后勤、学院联盟）一律随主联盟同方，名单维护在 `scripts/battles.mjs` 的 `SISTER_ALLIANCES`，构建校验拦截跨方。
- **手填战役**：来源是 CCP 新闻、WarBeacon、EVE-KILL、论坛自报等其他口径时，总损失和各方人数、损失、记录条数照来源手填，全场数不能顶替分方数；取不到才写 `null` 并填 `stats_note`，0 只表示来源确认没有损失。字段见战役模板；窗口、星系、阵营映射与差异留素材。
- 正文按阵营分节，写各方的华人人物与华人军团。人物列传引用已有战役页时链到 `../../battles/<短名>/`，KM 链接照留。
- **相关视频**：页首推荐最多 8 个与本场直接相关的视频，B站为主，史诗档可含 1 个 YouTube。尽量兼顾各方视角，但不强求均衡，不为凑数或等量增删；没有合适作品就不显示。转载、合作按公开署名写明原作者，介绍只写已读到的内容，不编阵营或驾驶者。关联判断按[取材手册](research-method.md#来源对战役时区与战报)，字段格式见战役模板。
- 字段、正文结构与互链写法见[战役模板](battle-template.md)，流程用 `add-battle`；文风与红黑料规则同列传。

## 6. 素材归档

- **先留存，再决定是否入文**：搜索和接收材料时保留关键原文与必要上下文、出处、时间、作者／说话者和角色对应线索；暂不适合入文、无法归属或看不出用途的，也归档并写明待核问题或暂缓原因，不因当前用不上而丢弃。现实隐私不为留存而保存。
- **事件摘要用 Markdown 精炼**：外部图片、聊天记录、PDF 可能随时消失，读懂后把事件经过、关键原话、必要上下文、人物对应、出处和待核问题写进素材，不依赖原文件。不全文转录、不堆聊天流水账、不存文件名／哈希／原排版，不重复记处理过程。分清事实、来源方说法与推测，读不清的关键内容标出缺口，不补造。
- **少存二进制文件**：不批量备份图片或 PDF；只有文字无法替代的关键图才少量保留，并去除现实隐私。
- **B站结构化档案**：账号对应、频道 profile 与覆盖、作品公开元数据和状态统一放 `docs/bilibili/<UID>.json`，人物身份自动关联，不另存全员总表。具体事件、关键言论和作者回应归本人素材；视频、图文与旧专栏共用同一档案，与素材用稳定 UID／BV／图文 key 及素材锚点互链。流程见[档案说明](bilibili/README.md)。
- **军团结构化档案**：军团简介、CEO／执行关系观察、历史月份与固定all-time榜、公开账号组归`docs/corporations/<军团ID>.json`；跨团角色调查只维护一份共享记录，已收录身份仍从正式人物档案读取。榜单目标固定Top 100，已有all-time只作hint，不刷新；旧前50范围和缺失名单照实保留，不因迁移补齐或升级完成。不另建调查批次、日期命名的状态表；具体字段、历史未知实体与核读摘记见[军团档案](corporations/README.md)。
- 已收录人物的来源与检索记录 → 本人目录 `materials-<短名>.md`。
- 未收录或角色对不上的人，有独立事件或具体待查材料 → `docs/leads/<短名>.md`，并在 [docs/pending-characters.md](pending-characters.md) 登记一行；收录后移入人物目录。只有军团榜名片、同人账号对应及尚无故事的判断，归既有军团角色档案，不另建薄线索；共用事件已完整归档的，独有依据和缺口并回共享材料，备忘录直接指向正式档案。回顾一份线索时一并筛查同类重复入口，不等逐个点名；删除前保留独有证据、失败与排除依据、未读边界和具体待办，并更新有效引用。
- **材料位置不手填总索引**：`npm run materials -- "关键词"` 从人物、战役、来源、线索与 B站档案按需生成查询结果，用法见[取材手册](research-method.md#本地材料查询)。新增／迁移材料只改正式文件及确有待办的原队列，不另建人物总表、完成汇报或状态副本。旧索引已冻结为历史 JSONL，只按需检索，不能覆盖当前档案。
- **内部数据与清单**：ID、账号对应和多维状态用 JSON，同构榜单与逐行队列用 TSV，事件经过与原话用 Markdown；已有格式够用就复用，可推导结果不手填（见[仓库统一标准](repository-standards.md)）。迁移保留独有事实、失败与排除依据，未知保持未知，冻结历史不参与当前状态判断。只留未完成调查的队列、失败与排除记录，已完成的报告并入正式档案后删除，同一队列只维护一份状态表。
- **回顾材料时随读随整理**：再次阅读或修订某份素材时，检查其中的低价值操作流水账，如按日期记录“作品精选去重”“作品精选补足”、增删清单、完成汇报及重复状态。先将独有事实、来源、有效筛选依据、阅读边界和具体未完成事项并回对应事件或作品，再删除已无续查用途的记录；不按标题机械整段删除，不另写一份清理日志。新材料也不再追加这类流水账。只整理本次实际回顾的材料，不因此自动扩成全仓清理。
- 材料只写事实、说法和来源，不记录素材提供者身份或对话过程，不写“维护者确认”。
