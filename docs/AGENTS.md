# 文档与材料代理约定

适用于本目录及子目录，继承根目录指令。共同标准见[仓库统一标准](repository-standards.md)，分层维护见[指令治理](agent-instructions.md)。本仓库的规则主要由代理读取执行，规则类文档按下文“写给代理读”的要求组织。

## 职责与入口

- 列传、战役、军团各有一套规则、模板和验收：`rules-person.md`／`person-template.md`／`person-review.md`，`rules-battle.md`／`battle-template.md`／`battle-review.md`，`rules-corp.md`／`corp-template.md`／`corp-review.md`，互不引用写作标准，也不合并。
- 三类唯一共用的规则文件是 `terminology.md`（专名写中文）。列传与线索的归档在 `materials-person.md`，战役、军团的素材要求写在各自规则里；联网方法在 `research-method.md`（人物、战役专项在 `research-person.md`、`research-battle.md`，工具语法、B站细则与少用入口在附录 `research-tools.md`）；视觉在 `site-design.md`。其他入口只引用，不复制整段。
- `sources/` 存共享来源，`leads/` 存待查线索，`bilibili/` 与 `corporations/` 按自身 README 维护结构化档案，`reviews/` 按[增量复查](review-workflow.md)保存功能结论。已归人的素材进本人目录；改人物／战役文件须另读对应技能与目录指令。

## 规则文档：写给代理读

代理常只读一节、按条执行，并容易漏掉长文后段。规则、模板、验收和技能按以下要求写：

- **开头两三句**：说明这份文档管什么、什么任务该读、什么任务不必读；有边界（如“只验组件，不触发列传复审”）放在最前。
- **结构固定**：按“边界 → 流程步骤 → 字段或格式示例 → 判定标准 → 例外与不算 → 验收”排列。标题自解释，让代理只读一节也能执行；只在特定任务用的流程放文末附录，并写明触发条件。
- **硬规则显式集中**：底线、最低档、阈值、禁止项写成“条件 → 结论”，集中在对应小节开头，不散落在解释段落里。用“必须／不得”标硬规则，用“可以／一般”标判断空间；同一条不在多处换说法重复。
- **示例胜过描述**：字段结构给一段与当前校验一致的最小示例；判定标准给正反例各一。示例用虚构占位，不点名真实人物。
- **可检查**：每条规则要能让代理判断“做到没有”。写清命令、文件路径和完成标准，不写“注意”“尽量严谨”这类无法验收的提醒。
- **精简**：不写沿革、本轮任务措辞、机器路径或完成日志；不叠加“严禁／绝不／务必”式语气，一条规则说一次。长而谨慎的条文是缺陷，能删的限制先删。
- **与代码同步**：文档描述的字段、档位、展示或命令必须与脚本、校验和模板一致。改规则时检索同一事实在代码与其他文档里的表述，一并修正或在汇报中指出冲突。

## 局部约定

- 技术文档用中文，先说明目的与实际行为，再写必要步骤；正文历史来源可以保留原文。
- 接收、迁移与清理材料按所属类型的规则，列传与线索遵守[列传素材归档](materials-person.md)；用 `npm run materials` 定位已有档案，不另维护可推导的全员总表。完成状态必须与实际读过的范围一致。
- 改规则先找相应技能、模板、引用入口和调用代码，只维护权威段落；需要复查时登记候选与失效依据，不能声称所有旧内容已自动符合新规。
- 内部叙述材料按[材料 JSON](materials-json.md)维护，公开正文与规则说明用 Markdown；叙述中的链接使用相对路径，段落不硬折行。

## 验收

- 检查本地链接与锚点仍有效（被其他文档引用的标题不改名），指令副本运行 `npm run instructions:sync` 后由 `npm run instructions:check` 核对。
- 规则改动按上节核对与代码一致；改工具另跑相关测试。
