# 找料方法

取材手册。目的是**找故事**，不是凑完备档案：找到能写的料就可以先立传，以后再补（门槛见 AGENTS.md 第 2 节）。本文件只写通用方法，不提具体人物；人物材料写进本人 `materials-<短名>.md` 或 `docs/leads/`。

## 一、取材原则

1. **先问此人以什么出名。** 那件事必须是列传最重的一块。画像（常用船、星系、联盟）和料对不上时，说明还有没找到的。
2. **搜不到 ≠ 没料。** 验证码、403、外号撞常用词都是搜索失败，记为【搜索失败】停止该站请求，不当成零结果。
3. **找到就收。** 有出处的料全部入列；轻料并进相关块。对立说法并列，本人自吹与别人揭短对不上时并排放——往往最好笑。
4. **先留素材，再判断能否写。** 搜索到或收到材料时，尽量保存原始内容/关键摘录、必要上下文、出处、时间、作者或说话者及角色对应线索。暂时不适合写、归属不明或尚未核实的内容，归入对应人物素材或 `docs/leads/`，写明待核问题/暂缓原因，留待未来补写或复核；不因当前用不上而丢弃。不得为存档而保留现实隐私。

5. **野史不是科研，数字要量级不要精确。** 回答“他干过多少、干得多不多”，一个量级就够：几十（10–99）、上百（100–199）、数百（200–999）、上千／数千（1000 以上），正文就这么写，不写精确数。可以入文的有两类：免费页面上现成的汇总数，或者几张代表 KM。不为凑出准确总数逐年、逐月、逐号扫描，不批量补全几百张 KM，不为去重、核对口径反复请求。批量请求浪费 token，还会招来对方站点限流和风控；能用一次请求得到的量级，就不发第二次。

**归档以 Markdown 总结精炼为主。** 读懂图片、聊天、PDF 等素材后，只保存事件经过、关键原话、上下文、人物对应、出处和必要待核点，不做全文转录、聊天流水账、文件名／哈希／排版备份，也不重复处理过程。多人共用的事件摘要可放在 `docs/sources/`，人物素材只补与本人有关的增量。不要批量备份图片或 PDF，只有文字无法替代的关键图才少量保存去隐私版本。

**取材记录交给写作时，要提炼故事。** 缺口留在素材；围绕已有事件整理人物处境、利益冲突、互相打脸的说法与可推演的动机。第二来源、完整名单和准确人数不是普通社区故事的写作前置条件。来源说法可以直接入文并交代来路，正文发挥与验收按 AGENTS.md 第 4 节和 [写作验收与改写例](writing-review.md)。

### 按增量安排下一步

- **先定位本轮缺口。** 已有具体事件先读其原帖、公告和相关回复；已对应作者先追本人主题与互动网络；身份缺口先查头衔与角色互链，再作关键词发现。已知角色ID用查重、缓存或ESI解析，不为认名字重复打开EveWho／zKB网页。已有对应达到收录规则时，不另加必须自贴视频链接等前置条件。
- **名册先认人，再追故事。** 军团榜先批读头衔、完整简介并合并同人；有管理职责、FC自述、明确事件或作者入口的再展开。船型统计、逐条KM和完整战报只在解决具体指挥／战役问题时查，普通成员仅有KB入口就留素材，不用补齐战果代替人物故事。同类批处理复用已适用的取材与解码逻辑，不每团重写一套临时脚本。
- **检索看相关增量。** 返回普通词匹配、重复帖子或他人发言，不算本人物新线索；连续无增量按下方停止规则处理。新帖号、作者UID或具体事件出现后才转入相应分支。未达原目标但找到其他人的独立材料，也按实际作者留存，不能误归，也不能当作毫无收益。
- **批次以事实落档为终点。** 每批交代新增事件、身份对应、实际职责或可续查入口及归档位置，不用页面数、评论数、文件数代替成果。同批先核角色ID、术语、互链与索引格式，再写作和最终构建；同一会话已读规则只在规则变化或出现具体疑问时重读。大输出先落临时文件，缓存先查来源、标题和状态，再分段读相关正文。
- **验收留存和续查价值。** 归档后重读新增段，核对关键原话、作者、来源和待核点确实存在；构建通过不替代素材验收。已经读过但无相关增量的分支保留简短排除依据；评论加载失败保留明确入口与状态，后续有具体恢复条件才再查，不把“补完频道／所有折叠回复”自动当下一轮任务。

## 联网条件与预算（所有取材入口共用）

先复用素材、快照和检索记录。只有新增线索、影响本次内容的未查缺口、记录矛盾或明确刷新要求才联网；普通修订、换会话、缓存到期均不触发重查。军团榜单和名册跨人物复用。

- 请求预算是上限：关联人物首轮总计 30 次；EveWho 最多 8 次（搜索 4 次），zKillboard 搜索 6 次；失败、分页和跨脚本调用都计数。不自动续预算。
- 按站串行，EveWho 间隔至少 6 秒、ESI 1 秒、其他站 2 秒；有更严格规定时从严。榜单首批最多 10 人，明确编号系列首批最多 20 个名字，优先批量解析。
- 连续3次关键词检索无新线索停止该分支；403／429／412停止相应入口，不自动换路径或出口。B站API与Chrome分开记录，见B站节；其他验证码等待人工处理，超时停止。冷却到期不自动重试，恢复须有具体未查需求。
- 预算触顶、分页未完、接口失败均记覆盖缺口；不为“全部读完”无限翻页，不猜接口，不把失败当零结果。更大规模回查只在明确要求时另定范围与预算。

HTTP 取材脚本有单次运行限额和按站间隔，拦截状态跨运行保存至少 30 分钟；任务仍须统一计算多个工具的总预算。临时 HTTP 脚本也用 `researchFetch`，或按已声明批次上限创建 `createRequestGuard({limit})`，默认共享停止记录；不重置冷却文件续预算。浏览器工具另限制导航／评论分页，验证码可人工处理，等待超时才停止。无需联网时请求为 0 次。

失败记录保留实际 URL、读取方式、时间与状态码。HTTP 200 挑战页记为挑战页，不能改称真实 403；某次抓取 403 不证明网页对正常浏览受限，更不证明功能不存在。共享冷却读取 `researchHostStoppedUntil(站点)`，兼容旧 `.cache/research-cooldown.json`；新事件写入对应 `.json.d/`，不靠手读旧文件判断是否能请求。

## 二、四类取材入口（记录命中 / 零结果 / 搜索失败）

按当前问题选择入口，复用已有覆盖，不机械遍历四项。

### 1. 游戏画像（定位人物时按需）

`node scripts/research/profile.mjs <角色ID> [论坛用户名] > 画像.md`

先复用快照与已有画像；资料缺失且影响本次判断时补跑。环境先用 `npm run doctor` 检查，旧 Node 报路径错误应修环境，不能据此弃用画像或重新手写一套请求。

按预算汇总：头衔与简介全文、每段军团当时所在联盟、zKillboard 常用船/星系/高价值月份、凛冬论坛本人主题与回帖；并非保证一次全齐，未查部分留缺口。重点看：

- 本人写的角色简介，常常就是最好的料；
- 常用船 + 星系暴露玩法（Catalyst/Talos + Uedama、Niyabainen = 高安强暴）；
- 某月 ISK 暴增可作战役检索线索，不能直接判定战役规模或个人功劳；
- 凛冬论坛标题带敏感词（强暴、骗、举报……）的帖子必读。

**量级先看 stats，一次请求。** `zkillboard.com/api/stats/characterID/<ID>/`（网页版 `/character/<ID>/stats/`）已有按舰船分组的击毁数（`groups`，如货舰 513、跳货 902、逆戟鲸所在 941）、逐月击杀与 ISK（`months`），足以回答“打过多少货舰”“哪几个月最活跃”，直接取量级入文。还要代表 KM 时，从 `months` 挑一两个高峰月，取那个月的 KM，或用[高级搜索](#zkillboard-高级搜索asearch)只拿少量。不再细算口径、去重或补全。

需要细查时：zKillboard `api/kills/characterID/<ID>/year/<Y>/month/<M>/`（curl 要加 `-L`），只取选定的那一两个月；ESI `killmails/<id>/<hash>/`；DOTLAN 军团事件史。

**追历史 CEO 时查任期和角色归属。** 遇到军团旧事、踢人、封号或管理争议，打开 DOTLAN 对应军团的 `/events` 页，逐条看 CEO 辞任、接任记录，再用事件发生日期对上当时的 CEO 角色；接着核对历任角色是否属于同一人。DOTLAN 只记录角色换任，不证明换了真人。EveWho、ESI 军团页显示的现任 CEO，不能倒推旧事归谁管；某个小号的入团日期，也不能当作本人首次掌管军团的日期。把角色任期、本人对应和事件日期记进人物素材，再写归责。

**战役补漏。** 按各方总损失分中型（100B–不足 400B）、大型（400B–不足 1T）与史诗（1T 及以上）。综合 KB 与战役经历在同一红料里并列保留，正文结合人物处境、阵营与前后经历展开战斗并点评，不写成逐场报账后补一句俏皮话；列全已确认战役，记录窗口、阵营与参战／指挥依据，不以月度累计代替战报。

**先发现战役，再反查人物。** 大范围补漏先从 r/Eve 与 EVE 官方论坛的 AAR、战斗视频／复盘连载、招新帖中的 BR 找事件，个人 KB 作为补查入口。搜索搭配联盟全名／缩写、星系、`AAR`、`dread brawl`、`capital`、`battle report` 和战报域名；不只搜 FRT，不把标题是否写金额当作筛选门槛。评论中的修正版 BR、第二阶段和合并战报也要留存，长连载按实际读取页码记覆盖。

- 建事件清单：原帖与作者、发帖日、实际战斗日、全部 BR／related 链接、来源方说法、已核窗口／星系／分组／总损失、待核项。帖子标题金额只作线索；官方论坛里的玩家发帖也不是 CCP 官方定论。
- 多日累计、多场合计、结构与资产估值不冒充单场战损；同一场的分段／修订战报按 KM ID 去重，保留版本与窗口差异。宽窗口多星系 BR 中，人物仅在无关星系命中，不据此认定参加主战。
- 取得完整战报后，对照全部收录号与已对应主力小号，再查具体舰船、阵营和 Monitor／动员／复盘依据。高价 KM 样本可发现人，不能定整场金额，也不能用零命中排除参战。
- 共享事件摘要放 `docs/sources/`，人物增量归本人素材；只有战役规模与本人参战均有依据才补战绩正文。区分“候选发现”“战报已核”“人物已对照”“正文已增补”，入口失败或预算用尽记覆盖缺口，遵守本页停止规则。

**小号也查，但号多时最多查两个。** 从本人素材与别名取已对应的小号，按人合并战役；只查 KB 最好或最近最活跃的一两个号（优先参与击杀价值 ≥100B 的主力号），其余小号不查，已有直接证据的照样入料。小号常与大号落在同一张 KM 上，多查一个号几乎不增加料。高价值 KM 样本未命中时，再查主力号在该星系、该月的记录；不把样本零命中当未参战，不把各号累计直接相加。

### 2. 贴吧（eve欧服吧为主，eve吧只作低优先级线索）

**先核服务器，再认人物和事件。** eve 吧大部分内容来自国服，对本站属于低质量、低优先级线索来源，不作为默认补查入口。只有已有具体欧服交集线索时才查；命中后先核吧名、正文中的服务器、事件时间、角色与战时组织。同名人物、PIBC 等跨服沿用的组织名、中文角色名或“EVE”字样都不能单独证明属于欧服，eve欧服吧里的国服回忆也须区分。

- 明确属于国服、且没有独立欧服交集的事件，标为【国服排除】，撤出待收录队列；保留简短来源摘要防止重复误收。
- 服务器不明的材料标为【服务器待核】，不直接转为欧服人物故事；找不到欧服角色不是将国服 ID 当中文外号的依据。
- 已有欧服身份的人，其国服旧事须明确事件发生在国服并另记同人依据；不能因同名把国服争议移植给欧服角色。来源质量与爆料立场分开：单方说法可以入料，服务器与人物归属仍须对上。

首选匿名客户端工具，不弹验证码：

| 要做什么 | 命令 |
| --- | --- |
| 站内搜索 | `node scripts/research/tieba-client-search.mjs "eve欧服 关键词" 4 eve` |
| 翻帖子列表（约两年） | `node scripts/research/tieba-client-forum.mjs eve欧服 1 10 temp/frs.tsv` |

| 某账号发帖列表 | `tieba-client-user.mjs <帖子.json> <用户名片段> [1主题\|0回帖]` |

- 关键词带“eve欧服”；外号撞常用词时改搜事件词、联盟名、英文角色名。
- 搜索命中常只是一句回帖，点进主题读完整楼层。截图里的聊天人名、KM 常常就是角色名。
- **角色对不上时，先读已取得的全文与帖尾，不只看截断摘要；未读部分保留缺口。** 长帖作者常在后期楼层贴游戏聊天记录（`[ 2025.02.28 13:44:48 ] 某某 > ……`），自己的角色名就在其中；先看最新楼层（网页“倒序”，脚本用 `1 --reverse`）。客户端 `r=1` 仅将当前页倒排，第一页仍是早期楼层，必须先取 `total_page`，再从末页读起；倒序 `has_more=0` 不能当作整帖结束。再拿帖中回忆的具体击杀（日期、船型、总值、掉落）去 zKillboard 对，用户名的变体（binkcn → Bink Wang）用 `npm run find` 试。检索脚本的结果可能混入其他吧，逐条确认吧名；前三页没命中目标吧，不算零结果。
- 账号追踪同时核对客户端的展示名 `name_show`、原用户名 `name` 和 uid。展示名变成“贴吧用户_……”时不能因此判断此人没发帖；`hide_post=1` 只说明回复列表隐藏，转查主题、站内命中与他参与的帖。
- **楼中楼必须单独分页。** 主楼的 `sub_post_list` 往往只是两条预览，按当前问题与预算读取 `/c/f/pb/floor` 的相关页，并用回复 ID 去重。记录声明数量、可见数量、页码与失败；分页结束但数量不足时仍记缺口，不能声称完整。删除、折叠、计数滞后和限流都不可当作无料。
- **回查要保存覆盖清单。** 分清“首尾抽查”“主楼分页完成”“楼中楼可见分页完成但计数有差”“阅读并归档”“正文已增补”。API 成功不代表人工已经看过；HTTP 403/429 立即停止这一批请求并冷却，续跑不能跳过之前失败的条目。
- 原始输出可能含现实隐私，只放临时目录。

### 3. 搜索引擎

先 Google（代理自带网页搜索，加 `site:tieba.baidu.com`）和必应，最后才用百度/360（容易限流）：

- `node scripts/research/baidu-search.mjs "某某 eve欧服吧"`；按需选择 `--so`（360）或 `--bing`，不因被拦自动轮换。
- 批量：`node scripts/research/batch-search.mjs <清单.tsv> <输出目录>`，固定引擎、每轮最多 10 条，缓存跳过；遇拦截整批停止。

| 目的 | 关键词（“某某”换成中文名、外号、角色名） |
| --- | --- |
| 评价 | `某某 eve欧服吧`、`如何评价某某` |

### 4. B 站（与贴吧同等重要）

- **发现方向**：人物的 B站 线索先查 [B站UP检索名单](bilibili-uploaders.md)，命中就复用UID／BV，未命中在素材记“待板块扫描”；素材里已有确切UP名、只缺UID的，可直接用户搜索该名一次，不按人名、外号或角色名搜 B站。本人简介、帖子等已对应账号贴出的链接可直接读，读后补进名单。新增发现只按名单里的扫描队列，以 EVE 宁静／欧服话题和事件汇总 UP、按 UID 去重登记，再反查人物。确定的 UID／BV 和失败记录直接复用，不重扫成功页。
- **先读空间，再定作品候选**：已对应UP首次调查或补作品精选时，先核空间简介、视频／图文数量、合集与系列；同一人物有多个已对应UP账号时逐个核空间，候选或仅在作品里被点名的账号不混作本人账号，跨账号候选合并去重后总共最多选5个；分别查看“最新发布”和“最多播放”排序，核对当前选中排序，记录实际页次与覆盖。最新页用于近期活动，最多播放页用于寻找历年代表作，两者不能互相替代。已有成功缓存可复用，但必须含排序和作品内容；未查最多播放不能把最新页里较高播放写成全频道最高。按人物创作主线、重要事件与系列补候选，不只追最近发布，也不把整个频道补完当目标。
- **候选之后才读作品**：将最新、最多播放、代表系列和已知事件的候选合并去重，再按预算读简介、选集、作者公开文字与评论。播放量用于发现候选，不直接证明作品优秀；评论用于补作者故事、互动和争议，不替代空间调查，也不能凭热评评价画面、剪辑、讲解质量。默认读文字，不为找角色名逐段播放长视频；转载视角和标题战损不直接归本人。联合制作的视频不作为作者本人的推荐视频，不计入最多5个精选名额。合作经历与作品中的具体事迹仍可归档、入文；另核公开创作团队与本人具体署名，owner只说明上传者，不把合作独算本人。跨平台对应按 `AGENTS.md` 第2节。
- **身份、阅读与精选分别判断**：本人账号对应且已见足量EVE投稿，就按标签规则保留UP身份；未读完作品、评论未加载、未做精选均不是撤掉身份的理由。“B站”是平台／身份标签，不作人物别名；清理别名不连带清理身份标签。精选最多5个；前两个候选质量较高时，继续从最多播放、合集和相关事件扩大候选，按批次补读，选足5个后再收尾，不能把首批读取上限当整项任务上限。只有继续筛选后确实不足5个合适作品才少选，素材须记筛选范围、具体淘汰原因与未读缺口；未读或预算／访问限制只能记未完成，不能判成作品质量不足。逐条写标题、链接和基于实际内容的推荐理由；仅见标题／计数者只留候选。未读影像时，推荐理由只能落在已读公开文字提供的具体内容上，不声称看过或评价视听制作；没有足够内容依据就明确精选待补，不为填满名额硬选。
- **精选不套人物立传门槛**：本人带队、实战记录、教学与系列创作本身就是作品看点，不要求每条另有独立社区事件、评论笑话、作者答疑或“本人制作”的声明。已对应本人频道、角色简介自荐与本人系列的实战作品，结合这些上下文判断归属；简介只有“视频已加速”、评论少，都不是排除理由。评论用来补充内容，不作推荐的必需条件。推荐语说明已知主题、人物特色和适合谁看；没有读过视听，不评价具体操作、剪辑或画面质量。明确转载他人作品时分清原作者与本人的整理、译介或评论；不能把外网链接一律当不合格，也不把别人的驾驶与指挥归给UP。联合制作仍按上一条排除。内容确实尚未取得的记为待读，不以“个人加工说明不足”冒充作品筛选结论。
- **关注度筛选**：暂用粗筛，播放不足1000且评论不足10的作品不主动续读，只留标题、出处和当时计数；一项明显受关注的仍可候选。先利用已有计数筛选，不先批读再剔除。空间视频卡片的播放旁计数是弹幕，不当作评论数；评论数以作品公开元数据的`stat.reply`或评论区为准。只有空间计数时，先核作品元数据，不能据弹幕少判评论少。这个粗筛用于安排未读作品，不代表作品质量或收录门槛；已读材料与已有故事保留，频道不以全量补完为目标。
- **先验证读取方式**：新增或修复评论读取方法时，先用一个有评论的页面核对实际评论正文与覆盖，再扩批；页面可读不等于评论已读。评论停在加载态时，先用真实鼠标滚轮向下滚动窗口，等待2秒再查正文；仅调用DOM的`scrollIntoView`不保证窗口实际滚动，也不保证触发懒加载。取得一次空评论结果后先查加载状态，不把同一失败读取方式批量套到剩余作品。
- **登录复用**：已授权读取 B站 Cookie。API通过 `bilibili-session.mjs` 从可连接的 Chrome B站标签取会话，仅在请求内存中使用，不存文件、不进日志或Git，不读其他网站凭据。Chrome沿用持久配置；日常窗口与独立窗口的登录状态可能不同。
- **失败处理**：API遇403／429／412／-352，停止该站API并冷却至少30分钟，不换接口或出口；这不等于Chrome网页也不可读。Chrome遇验证或拦截也停止并单独冷却，不重置停止记录续跑。
- **覆盖边界**：等页面正常加载，不刷新加载壳。核对投稿总数、可见BV与页次；视频页最多取20个已加载主评论线程，未翻页或展开楼中楼。评论在shadow DOM里，正文没显示不代表无评论；合作账号注销也不代表视频失效。只把实际读到的内容记入素材，保留分页与身份缺口。

| 入口 | 命令与限额 |
| --- | --- |
| API | `node scripts/research/bilibili.mjs <命令>`：`user`、`search`、`videos <UID>`、`info <UID>`、`video <BV1,BV2,…> [评论页数]`、`dynamics <UID>`。每个关联UP／事件约15次请求，最多选5个有料视频批读；成功缓存位于 `.cache/bilibili/`。 |
| Chrome | `node scripts/research/bilibili-chrome-read.mjs <公开网址或清单.json> <.cache/输出目录> [最多页数]`。Windows Node≥22＋系统Chrome；清单为 `[{"url":"公开网址"}]`，支持投稿、视频、动态／专栏和搜索页。默认30页，单批上限60页；批量范围与总预算先写进唯一续查队列。 |

| 要做什么 | 命令 |
| --- | --- |
| 搜索（经搜狗知乎站内，知乎自带搜索未登录无结果） | `node scripts/research/zhihu.mjs search "关键词1" "关键词2" [页数]` |
| 读问题 / 文章与评论（预算内） | `node scripts/research/zhihu.mjs read <网址>...` |
| 列某人文章与回答（预算内） | `node scripts/research/zhihu.mjs user <主页或url_token>` |

- 宽泛关键词（“eve欧服”）九成是萌新问答，费验证码；搜事件词和人名：`eve FRT`、`如何看待 某联盟`、`某某 eve`。标题含“如何看待/如何评价”加事件的优先读。

### 外网（外国联盟、华人被老外爆料的戏多在这里）

- **Reddit（r/Eve）**：reddit.com 网页、`.json` 都被拦，代理自带网页搜索也几乎搜不到具体帖。读帖一律用 `node scripts/research/reddit-thread.mjs <帖子ID或网址> <临时.json>`：走 pullpush.io 存档，打印正文和已取得的评论，未完分页留缺口（评论编号 ← 上级编号、作者、日期），原始数据存进临时文件。
  - 按关键词找帖：`node scripts/research/reddit-search.mjs "\"Army of Mango\"" [posts|comments] [subreddit=Eve] [条数]`（同走 pullpush）。网页搜索找不到帖子时，先找引用过 r/Eve 的英文二手文章（Talking in Stations 节目页、tagn.wordpress.com、imperium.news、New Eden Post），它们的链接列表常给出原帖编号。
  - **限流**：pullpush 对密集请求回 429（并声明不给代理免费抓取），Wayback 也会 429。脚本遇 429 立即退出；后续有新需要才评估恢复，不循环重试、不换站硬刷。
  - 存档接口一次最多回 100 条评论，脚本在预算内翻页，未完留缺口；不要把单次响应当全文，曾因此漏掉三分之二评论，包括认出当事人的那条。
  - 网址里 `?c=…` 这类分享参数不是评论编号，定位不到具体评论，直接读全帖。
  - 截图只有 `preview.redd.it` 链接，存档不描述图片内容；需要时另行下载。
  - 涉及华人的帖，评论区常贴贴吧或 B 站链接，顺着去读；爆料人常把军团介绍、联系方式昵称和角色名对起来，这类评论最有用。
  - 帖中说的角色名常有出入（缺前缀、拼写差一点）：ESI `POST /universe/ids/` 查名字，再看相关军团的 `ceo_id`、`creator_id`，用 `npm run find` 确认。
- **官方论坛**：forums.eveonline.com 的 `search.json?q=关键词`，多试几组英文关键词（人名、联盟名、事件词）。
- **凛冬论坛**（forums.winterco.org，有 `.json` 接口）：常有 r/Eve 戏的中文转述。
- **帖中链接的 Google Docs**：`/export?format=txt` 取全文。
- 结论按实际覆盖表述；未查渠道或被拦入口写缺口，不为证明“查不到”反复查询。

## 三、原帖读不到时

- 贴吧网页被拦：记录失败并停止；有具体新需要时再选择其他公开来源，不自动换工具重试。
- 帖子被删：Google 搜标题和帖子号，查 Wayback `https://web.archive.org/web/<时间戳>id_/https://tieba.baidu.com/p/<帖子ID>`、archive.is。
- 只有搜索摘要也能当来源写（“据某帖摘要”），不必因为读不到全文就放弃。

## 四、发现新人物

按名字找只能找回已知的人。改用：

以社区帖子、回帖和作者网络为主线，名册作补充入口；一条入口的零结果不能代替另一条：

1. **社区故事发现人物**：对贴吧帖子列表的“标题 + 首楼”按职务词（总监、CEO、团长）、冲突词（弹劾、背刺、澄清、骗、跑路、封号、悬赏）、叙事词（前传、始末、回忆、经历）加分，招新、交易、求助减分；叙事分数与回复量是两条独立的候选入口：高回复帖不因标题普通、招新、求助或首楼无冲突词而淘汰。数字加物品或事件词的标题也要抽样读，不能只看冲突词。将回复量前列的中性帖单独排队，至少读首尾和楼中楼，再决定是否扩为全文；同一吧、同一批的相对排名优先于固定阈值。
2. **按楼主 uid 聚合、追被点名者**：短期连发长帖、连开十来帖的楼主本身可能就是名人；回帖多但只开过一帖的人也可能是关键人物，不能只按发主题数筛。楼中反复出现的人名、`@`、别名和“这位就是……”“又是他”，都转为候选并查重；角色藏在回复里时，不能因为标题和楼主不是他就跳过。用 uid 合并改名账号，保留原用户名和展示名。
3. 排除已读帖子号再看。列表接口只回溯到约 2024 年中，更早的用站内搜索 + 上述关键词。
4. **名册补充**：CCP 各届 CSM 候选公告与竞选区、联盟锦标赛队伍名单、重大事件战报、军团管理名单可补漏，逐名对照本站列传、人物素材和待确认角色备忘录。候选公告中的 `Chinese`、`中文`、华人军团或联盟只是优先核对线索，不凭姓名、所在联盟或贴了中文版就认定与华人圈有关；参选和当选分开核对。发现人后仍要回到社区帖子找故事。

每次名单反查记下来源、覆盖的届次或事件、逐人的“已收录 / 新候选 / 关联待核 / 排除”及依据。只写“查过 CSM”不足以说明覆盖；未逐项对照的届次继续列为未查。查到本人公开竞选与角色对应、已有一件有出处的事，就按收录规则立传；身份未对上才进 `docs/leads/` 与角色备忘录。

有自己的独立人物事件（不只是别人回忆里路过一句）的人就登记或按收录门槛立传。仅有简介幽默、个人自嘲、普通聊天、泰坦／超旗战果签名、KM收藏和KB分析的，不自动立传；先保存素材、身份与来源，再追具体社区事件、争议或行为影响。有任职依据的军团CEO及已有职务或具体Monitor等指挥依据的FC，按AGENTS.md保留短篇；联盟重要管理者同。军团内部管理岗按普通成员算，只有职务或单条轻料时先补料，补不到归线索。

## 五、已知的坑

- 角色名以本人或当事联盟写法为准；同一外号可能指不同人，用游戏数据或原帖区分。
- **小号查漏按下方触发条件执行，先检查已有覆盖。** 找到收录号不等于找全本人；不等别人逐个报号，也不以 KB 名字检索没出现为完成依据。
- B 站视频被删且认不出作者时不引用。
- **低可信来源**：声望哥（小♂凯／Sirses／Wibrik2021）与咪咪（彭铁柱／koko1 k）同档。他们对别人的指控、定性和自报数字可以入料，但正文写成本人一面之词，笑点落在发帖人身上；不单凭其说法给第三人定黑料、职务或标签，有他人独立说法时以他人说法为主线。他们发帖、点名、悬赏等本人行为照常算本人的料。
- Playwright 报 “Executable doesn't exist”：运行 `node node_modules/playwright/cli.js install chromium`。


华人联盟找人还须查 **ESI 联盟执行军团**：从 `executor_corporation_id` 取执行公司，优先逐个追现役角色的公开头衔、职责和社区事件；同人小号并回原人物。先复用现役名册、历史 CEO 和军团榜单，后两者不能代替现役名单。每轮首批最多十人，记任期、覆盖与未查项，再按线索展开。

## 六、小号查漏（有需要才补查）

沿已有身份线索选用以下入口，不把它们变成每次修订的必跑清单；统一遵守上方联网条件与预算。

- **名字扩查**：从角色名、aliases 拆词根，查编号、大小写／形近字及用途前后缀。明确系列才用 ESI `POST /universe/ids/` 有限批量补查，不默认穷举编号。
- **EveWho 前缀搜索**：`/autocomplete/<小写且 URL 编码的词根>`，取 `suggestions` 中 `data.type == character`。每类最多 10 项，满额记截断，只在预算内拆有线索的分支；不是错拼容错。接口说明见[公开源码](https://github.com/zKillboard/evewho/blob/master/www/controllers/autocomplete.js)。KB 自动补全可能漏掉无击杀的号。
- **军团榜单反查**：从当前或相关历史军团的高 KM 榜，选少量候选读头衔、完整简介，与全站中文名、别名及素材对照；可找到英文名字不同的小号甚至主号。使用 `api/stats/corporationID/<ID>/` 的 `topAllTime` 角色榜，别把近期 `topLists` 或有限榜单当全体成员。
- **月份口径**：`/corporation/<ID>/top/` 默认当前月，`/top/year/<Y>/month/<M>/` 取指定月。`topAllTime` 不替代月榜，未标日期的 `topLists` 不推断为最近完整月。先看返回字段与数据类型，再记录实际窗口、榜长、取得状态和已核身份；请求失败只留缺口。
- **身份核对**：结合自报头衔、角色互链、相近名字与当前／历史同军团、时间重合判断。同批建号、同步入退团可加固对应；只有“FC”等常见头衔或同联盟不足以合并。退团不抹掉已建立的同人关系。
- **补录**：明确同人的名字、ID、对应依据与来源写入 aliases 和本人素材，战役按自然人合并叙述，逐号统计与核对留素材，各号累计不相加。发现主号时记录择号依据；未对上、未查和失败分别留缺口，不另立小号传。

## 七、监视者驾驶员反查

华人联盟或军团的Monitor驾驶员是高优先级FC主小号线索，主动从已取得的战报、KM和船型榜查漏，不只查被点名者。按战时归属筛选；联盟有外语成员时继续核对军团、头衔与中文社区交集，不将整个阵营视为华人个人。

先对照本站收录号、aliases与素材中的历史小号；再查公开中文头衔、简介、同词根及当前／历史军团。明确对应者合并原人物；有独立故事且角色对得上者直接立传；未对应者在docs/leads备案并登记pending-characters。备案至少写角色ID、代表KM、时间、战时军团／联盟、已查项和缺口。监视者支持参与指挥，不直接证明总指挥，也不能单凭同船型或同联盟合并真人。复用共享样本，遵守统一预算；高值抽样未命中不当作没有驾驶记录，未全扫则说明范围。按军团／联盟查驾驶员用下文高级搜索：攻击方栏放军团或联盟加 Monitor，选 In。

### 系统 Chrome 月榜读取

已有明确浏览器读取需要时，运行 `node scripts/research/chrome-read.mjs <zkillboard网址> <.cache/输出前缀>`。WSL自动通过Windows Node连接系统Chrome，使用独立profile和仅本机CDP，不读取日常浏览器资料；保存正文、表格、角色ID及击杀链接。月榜后加 `ship/45534/` 可查Monitor，先核Top Ships确实只剩Monitor。KM的“List all pilots”需展开后再核完整参战名单；默认名单不能算完整。游戏存在伤害显示 bug，显示 0 伤害不代表实际零伤害，不据此评价人物或作为讨论素材。导航仍计预算，验证未通过则停止并留缺口，不把打开窗口当取得数据。

### zKillboard 高级搜索（asearch）

stats 回答不了、又确实需要 KM 名单时才用，例如“某军团谁开过 Monitor”，或为某个说法找几张代表 KM。只问“多不多”时先看 stats。一个问题一条精确筛选，默认 `--ids-only` 或 `--details` 十张以内；不按年、按月、按船型、按小号循环跑，不全量补全：

`node scripts/research/zkill-asearch.mjs <asearch网址或#后的JSON> <.cache/输出前缀> [--details N] [--ids-only]`

脚本把 `#` 后的筛选条件直接译成查询参数，在独立 Chrome 里分页取全部击杀 ID（浏览器只用来通过 Cloudflare）；随后用 zKB API 与 ESI 补全最新 N 张（默认 100），输出 `.json` 与 `.tsv`。tsv 的 `focus_side_ships` 列记下筛选点名者在每张 KM 上的身份与所开船型，用来核对查到的是不是想要的；脚本提示“没找到筛选点名的参与者”时先查筛选写法。

**先想清楚要回答的问题，再按问题写精确筛选。** 下面的写法与例子用来理解工具，不是固定配方：只放回答问题必需的条件，不相干的条件（如查强暴时限定攻击方船型）会漏掉真实记录。服务器每页 100 张、最多 10 页；时间段满额时脚本会对半拆段重查，这只是兜底。命中成百上千、要拆段，通常说明筛选写宽了，先收紧再补全。**零结果先拿一个已知会命中的同类筛选对照**（同一人换一条常开的船），服务器查询超时也会回空列表。筛选 JSON 的写法：

- **栏位**：`attackers`（攻击方）、`neutrals`（网页上的 Either，任一方）、`victims`（受害者）、`items`（掉落物品）。每项写 `{"type":…,"id":…}`，type 用 `characterID`、`corporationID`、`allianceID`、`shipID`（船型）、`groupID`（舰船分组）、`systemID`、`regionID`。
- **连接方式**（`buttons` 里的 `<栏位>-and`／`-aand`／`-or`，Either 栏写 `either-…`）：And 是每项各自匹配任意一名参与者；Or 是任一项匹配；**In（`aand`）要求同一名参与者同时满足全部项**。“某人开某船”必须把角色和船型放进同一栏并选 In；角色放攻击方、船型放 Either，查到的是“他在场且有人开这船”，舰队战里会混进大量别人开的船。
- **标签**（`buttons` 里写 `label-<标签>`；同组任一，跨组同时满足）：`ganked`（高安强暴：攻击方随后在同星系被 CONCORD 击毁；不含太空舱、战争、awox 与 100 万 ISK 以下，且只标 2018 年 2 月底以后的 KM，更早的强暴要改用 `loc:highsec` 加时段另查）、`awox`、`solo`、`#:1`／`#:2+`…`#:1000+`（参与人数）、`loc:highsec`／`lowsec`／`nullsec`／`w-space`、`isk:1b+`／`10b+`／`100b+`／`1t+`、`capital`／`super`／`titan`／`capinv`（有旗舰参与）、`tz:au`、`cat:6`（只看舰船）、`pvp`、`npc`。
- **时间**：`buttons` 含 `custom` 并写 `dtstart`、`dtend`（UTC，`2020-01-01T00:00`）；全时段写 `alltime`。排序 `sort-date`、`sort-desc`。
- `victimsonly`／`attackersonly` 按钮与 `includeAssociates` 只影响网页侧栏的排行汇总，不改变击杀列表。
- 船型等 ID 用 ESI `POST /universe/ids/` 或 `/universe/names/` 核对，不凭记忆写（Monitor 是 `45534`）。

例：

```text
某人开 Monitor 的全部 KM
{"buttons":["alltime","attackers-aand","sort-date","sort-desc"],"attackers":[{"type":"characterID","id":<角色ID>},{"type":"shipID","id":45534}]}
某人参与的高安强暴（不限攻击方船型）
{"buttons":["alltime","label-ganked","sort-date","sort-desc"],"attackers":[{"type":"characterID","id":<角色ID>}]}
某联盟谁开过 Monitor（tsv 的 focus_side_ships 即驾驶员名单）
{"buttons":["alltime","attackers-aand","sort-date","sort-desc"],"attackers":[{"type":"allianceID","id":<联盟ID>},{"type":"shipID","id":45534}]}
```

一次脚本运行计 1 次 zKillboard 搜索。拿到的 KM 与驾驶员仍按本手册其他规则核对身份、归属与红黑分类；KM 上有名字只说明参与。
