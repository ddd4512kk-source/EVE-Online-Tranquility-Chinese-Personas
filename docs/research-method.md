# 找料方法

取材手册。目的是**找故事**，不是凑完备档案：找到能写的料就可以先立传，以后再补（门槛见[内容规则](content-rules.md)第 2 节）。本文件只写通用方法，不提具体人物；人物材料写进本人 `materials-<短名>.md` 或 `docs/leads/`。

## 一、取材原则

1. **先问此人以什么出名。** 那件事必须是列传最重的一块。画像（常用船、星系、联盟）和料对不上时，说明还有没找到的。
2. **搜不到 ≠ 没料。** 验证码、403、外号撞常用词都是搜索失败，记为【搜索失败】并停止该站请求，不当成零结果。
3. **找到就收。** 有出处的料全部入列，轻料并进相关块。对立说法并列；本人自吹与别人揭短对不上时并排放——往往最好笑。
4. **先留素材，再判断能否写。** 留存与摘要要求见[内容规则第 6 节](content-rules.md#6-素材归档)；归属不明的进 `docs/leads/`。多人共用的事件摘要放 `docs/sources/`，人物素材只补与本人有关的增量。
5. **野史不是科研，数字要量级。** 几十（10–99）、上百（100–199）、数百（200–999）、上千／数千（1000 以上），正文就这么写。能入文的是免费页面现成的汇总数或几张代表 KM；不为准确总数逐年、逐月、逐号扫描，不批量补全几百张 KM，不为去重或核对口径反复请求。一次请求能得到量级，就不发第二次——批量请求浪费 token，还招来限流和风控。

**交给写作时提炼故事。** 缺口留在素材；围绕已有事件整理人物处境、利益冲突、互相打脸的说法与可推演的动机。第二来源、完整名单和准确人数不是普通社区故事的写作前提；正文写法按内容规则第 4 节与[写作验收](writing-review.md)。

### 本地材料查询

- 跨人物／战役查漏或规则变更复查，先按[增量复查](review-workflow.md)筛候选、读相关段落并检查旧结论是否失效，不先加载数百篇全文。
- `npm run materials -- "人名／角色ID／事件词"` 定位正式档案与路径，搜素材正文加 `--full-text`。结果不代表已核读、事件成立或调查完成，具体依据沿结果中的 `material` 读取。追旧备注或别名才加 `--history`（冻结的旧索引），当前身份、收录与阅读状态仍回查正式档案。
- 大榜单用 `npm run research:query -- <TSV路径> --where 列=值` 先筛再分页读，不整表加载、不另存状态副本。两个工具都离线，参数见各自 `--help`。
- 跨平台身份用 `node scripts/person-identity.mjs <人物短名或角色ID>`；B站频道与作品用 `node scripts/bilibili-archive.mjs show <UID> [BV或图文key]`；术语用 `npm run glossary -- "词语"`。待认号与待撰事项沿[备忘录](pending-characters.md)及其原队列续查。

### 按增量安排下一步

- **先定位本轮缺口。** 已有具体事件先读原帖、公告和相关回复；已对应作者先追本人主题与互动网络；身份缺口先查头衔与角色互链，再做关键词发现。已知角色 ID 用查重、缓存或 ESI 解析，不为认名字重开 EveWho／zKB 网页。已达收录规则的对应，不再加自贴视频链接之类前置条件。
- **名册先认人，再追故事。** 军团榜先批读头衔、完整简介并合并同人；有管理职责、FC 自述、明确事件或作者入口的再展开。船型统计、逐条 KM 和完整战报只为解决具体指挥／战役问题才查；普通成员只有 KB 入口就留素材，不拿补齐战果代替故事。同类批处理复用已有脚本，不每团另写一套。
- **检索看相关增量。** 普通词匹配、重复帖和他人发言不算本人物新线索，连续无增量按停止规则收手；出现新帖号、作者 UID 或具体事件才转入相应分支。顺带找到的他人材料按实际作者留存，不误归，也不算白查。
- **验收留存和续查价值。** 归档后重读新增段，核对关键原话、作者、来源和待核点都在；构建通过不替代素材验收，没读完不说读完。读过但无增量的分支留简短排除依据；评论加载失败留入口与状态，有具体恢复条件才再查，不把“补完频道／所有折叠回复”自动当下一轮任务。

## 联网条件与预算（所有取材入口共用）

先复用素材、快照和检索记录。只有新增线索、影响本次内容的未查缺口、记录矛盾或明确刷新要求才联网；普通修订、换会话、缓存到期都不触发重查。军团榜单和名册跨人物复用。无需联网时请求为 0。

- 请求上限、按站串行间隔和拦截冷却由 `scripts/research/request-guard.mjs` 强制执行，临时脚本也走它；报预算用尽就停，不换脚本、不重置冷却续预算。浏览器工具另限导航与评论分页。榜单首批最多 10 人，明确编号系列首批最多 20 个名字，优先批量解析。
- 连续 3 次关键词检索无新线索，停止该分支；403／429／412 停止相应入口，不自动换路径或出口。B站 API 与 Chrome 分开记录，见 B站节；其他验证码等人工处理，超时停止。冷却到期不自动重试，恢复须有具体未查需求。
- 预算触顶、分页未完、接口失败都记覆盖缺口，写实际 URL、读取方式、时间和状态；不为“全部读完”无限翻页，不猜接口，不把失败当零结果。更大规模回查只在明确要求时另定范围与预算。守卫用法和失败判读细节见[取材工具细节](research-tools.md#请求守卫与失败记录)。

## 来源对战役：时区与战报

贴吧、B站、知乎、截图、论坛回忆等任何来源要对上战役，都按本节判断。

- **中文日期先换算 UTC**：中文来源的日期和“凌晨／晚上／半夜”默认是北京时间（UTC+8），换成 UTC 再对战报窗口；北京时间凌晨常落在 UTC 前一天，跨午夜的战斗可能跨两天。带 Z 或时区的元数据时间戳优先，且不再减 8 小时；网页显示时间可能随浏览器时区变化。只有中文日期、缺时区的，候选保留 UTC 前一天与当天，不伪造确切时刻。保留原文日期与换算依据，不只凭日历数字或“晚上／清晨”的措辞排除。
- **发布日不是交战日**：大战主题的帖子、作品与战役日相差不足 5 天（UTC，多日战役取离区间最近的一天），又无相反线索，按高度可能相关处理，不因标题没写星系、正文简短或空白而排除。明确指向别场、别时期、别服务器的不凭近日期硬配；宽窗口、同星系连战和多场合集记清范围。
- **来源附带的 BR 与本站主报不同**：BR／KM 的实际时间地点对上本场即确认关联，不必与主报 URL 相同；链接文字本身不替代时间地点核对。不同 BR 记进本场素材，注明与主报的窗口、分队差异，不自动替换主报、不合并统计，损失不混算；主报日期不随来源标题改。来源所属战役已有明确依据时，里面另一场的 BR 只作附链差异保存，不推翻关联。未对应已有战役的先核星系、日期、范围和战役门槛。
- 关联与参战视角分开记：相关不证明属于某方、本人驾驶或指挥，视角未核清也不撤销已成立的关联。

## 二、四类取材入口（记录命中 / 零结果 / 搜索失败）

按当前问题选入口，复用已有覆盖，不机械遍历。

### 1. 游戏画像（定位人物时按需）

`node scripts/research/profile.mjs <角色ID> [论坛用户名] > 画像.md`

先复用快照与已有画像，缺失且影响本次判断时补跑；报路径错误先用 `npm run doctor` 修环境，不弃用画像或另写一套请求。脚本按预算汇总头衔与简介全文、各段军团当时所在联盟、zKillboard 常用船／星系／高价值月份、凛冬论坛本人主题与回帖，未查部分留缺口。重点看：

- 本人写的角色简介，常常就是最好的料；
- 常用船 + 星系暴露玩法（Catalyst/Talos + Uedama、Niyabainen = 高安强暴）；
- 某月 ISK 暴增可作战役检索线索，不能直接判定战役规模或个人功劳；
- 凛冬论坛标题带敏感词（强暴、骗、举报……）的帖子必读。

**量级先看 stats，一次请求。** `zkillboard.com/api/stats/characterID/<ID>/`（网页版 `/character/<ID>/stats/`）有按舰船分组的击毁数（`groups`，如货舰 513、跳货 902、逆戟鲸所在 941）和逐月击杀与 ISK（`months`），足以回答“打过多少货舰”“哪几个月最活跃”。还要代表 KM 时，从 `months` 挑一两个高峰月取 KM，或用[高级搜索](#zkillboard-高级搜索asearch)只拿少量。

解读 `topShips` 或 KM 船型前，用 ESI `universe/names`／`universe/types/<ID>/` 或已核舰船表解析 ID，不凭记忆认船；`appearances` 不等于全生涯使用次数。Monitor 的 typeID 为 **45534**（groupID 1972），**35683 是 Hecate**，不能当指挥依据。自动 `fc` 标记只作线索，实际指挥按内容规则第 3 节“指挥依据”核。

需要细查时：zKillboard `api/kills/characterID/<ID>/year/<Y>/month/<M>/`（curl 加 `-L`），只取选定的一两个月；ESI `killmails/<id>/<hash>/`；DOTLAN 军团事件史。

**追历史 CEO 查任期和角色归属。** 军团旧事、踢人、封号或管理争议，看 DOTLAN 对应军团 `/events` 的 CEO 辞任／接任记录，按事件日期对上当时的 CEO 角色，再核历任角色是否同一人——DOTLAN 只记角色换任，不证明换了真人。EveWho、ESI 显示的现任 CEO 不能倒推旧事归属，小号入团日期也不是本人首次掌管军团的日期。任期、对应和事件日期记进素材，再写归责。

**战役补漏。** 分档与正文写法见内容规则第 3、5 节。人物页的战役反链自动生成，素材只补战报看不出的参战／指挥依据，不以月度累计代替战报；正文只作总结性点评，不逐场报账。

**先发现战役，再反查人物。** 大范围补漏先从 r/Eve 与 EVE 官方论坛的 AAR、战斗视频／复盘连载、招新帖中的 BR 找事件，个人 KB 只作补查入口。搜索搭配联盟全名／缩写、星系、`AAR`、`dread brawl`、`capital`、`battle report` 和战报域名；不只搜 FRT，不以标题是否写金额作筛选门槛。评论里的修正版 BR、第二阶段和合并战报也留存，长连载按实际读取页码记覆盖。

- 读 BR 先打开实际页面的分队区，展开完整组织列表，保存队名、组织链接／ID、逐方人数、金额和损失条数。related API 无 `teams` 时继续读网页；只取到部分折叠列表不算读完；页面未加载完就等数据出现，遇访问限制按停止规则。核对与归方边界按[内容规则第 5 节“战役”](content-rules.md#战役)，来源差异、采用理由及快照统计差异留素材。
- 建事件清单：原帖与作者、发帖日、实际战斗日、全部 BR／related 链接、来源方说法、已核窗口／星系／分组／总损失、待核项。帖子标题金额只作线索；官方论坛里的玩家帖也不是 CCP 定论。
- 多日累计、多场合计、结构与资产估值不冒充单场战损；同一场的分段／修订战报按 KM ID 去重，保留版本与窗口差异。宽窗口多星系 BR 中，人物只在无关星系命中的，不认定参加主战。
- 取得完整战报后，对照全部收录号与已对应主力小号，再查具体舰船、阵营和 Monitor／动员／复盘依据。高价 KM 样本可用来发现人，不能定整场金额，也不能用零命中排除参战。
- 共享事件摘要放 `docs/sources/`，人物增量归本人素材；战役规模与本人参战都有依据才补战绩正文；失败或预算用尽记覆盖缺口。日期与来源 BR 的对照按[来源对战役](#来源对战役时区与战报)。

**小号也查，号多时最多查两个。** 从本人素材与别名取已对应小号，只查 KB 最好或最近最活跃的一两个（优先参与击杀价值 ≥100B 的主力号），其余不查，已有直接证据的照样入料；小号常和大号同上一张 KM，多查几乎不增料。高价值样本未命中时，再查主力号在该星系、该月的记录；样本零命中不等于未参战，各号累计不相加。

### 2. 贴吧（eve欧服吧为主，eve吧只作低优先级线索）

**先核服务器，再认人物和事件**（原则见内容规则第 2 节）。eve 吧只在已有具体欧服交集线索时才查；命中后先核吧名、正文所述服务器、事件时间、角色与战时组织。PIBC 等跨服沿用的组织名、“EVE”字样同样不能证明欧服，eve欧服吧里的国服回忆也要区分。

- 明确国服且无独立欧服交集的标【国服排除】，撤出待收录队列，留简短来源摘要防止重复误收。
- 服务器不明的标【服务器待核】，不直接转为欧服人物故事；找不到欧服角色时，不把国服 ID 当中文外号。
- 单方说法可以入料，但服务器与人物归属仍须对上。

首选匿名客户端工具，不弹验证码：

| 要做什么 | 命令 |
| --- | --- |
| 站内搜索 | `node scripts/research/tieba-client-search.mjs "eve欧服 关键词" 4 eve` |
| 翻帖子列表（约两年） | `node scripts/research/tieba-client-forum.mjs eve欧服 1 10 temp/frs.tsv` |
| 全帖回查 | `node scripts/research/tieba-client-read.mjs <帖子ID或网址> <临时.json> all --both`：正序和真正末页起的倒序主楼 + 每层全部可见楼中楼；再 `node scripts/research/tieba-client-dump.mjs <临时.json>`。原图用 dump 的 `--images <楼层数> <目录>` 下载 |
| 帖尾抽查 | `node scripts/research/tieba-client-read.mjs <帖子ID> <临时.json> 1 --reverse`；只看真正末页，不代表全帖完成 |
| 建立回查清单 | `node scripts/research/tieba-review-inventory.mjs <临时目录>`；加 `--probe` 续跑首楼/末页抽查，初筛不算全文阅读 |
| 断点续跑全文 | 原命令加 `--resume`，按同一 JSON 的覆盖记录跳过已完成主楼页和楼中楼，保留旧错误历史；帖号与顺序须与原文件一致 |
| 更新覆盖清单 | `node scripts/research/tieba-review-status.mjs <临时目录> <覆盖.tsv>`，只导出帖号、引用文件、覆盖与错误，保留人工处理栏；请求成功不自动写为已读 |
| 长帖分段阅读 | `node scripts/research/tieba-client-dump.mjs <临时.json> --floors 31:60`，含对应楼中楼；按实际楼层记阅读范围，截断的终端输出不算已读 |
| 按冻结清单补全文 | `node scripts/research/tieba-review-batch.mjs <临时目录> [本轮最多帖数]`，顺序跑，复用首尾与已完成全文，保留计数差，限流整批停止；抓取完成不代表人工通读 |
| 某账号发帖列表 | `tieba-client-user.mjs <帖子.json> <用户名片段> [1主题\|0回帖]` |

- 关键词带“eve欧服”；外号撞常用词时改搜事件词、联盟名、英文角色名。检索结果可能混入其他吧，逐条确认吧名；前三页没命中目标吧不算零结果。
- 搜索命中常只是一句回帖，点进主题读完整楼层。截图里的聊天人名、KM 常常就是角色名。
- **角色对不上时，先读已取得的全文与帖尾，不只看截断摘要，未读部分留缺口。** 长帖作者常在后期楼层贴游戏聊天记录（`[ 2025.02.28 13:44:48 ] 某某 > ……`），自己的角色名就在其中，所以先从真正末页读起（客户端倒序的坑见[工具细节](research-tools.md#贴吧客户端)）。再拿帖中回忆的具体击杀（日期、船型、总值、掉落）去 zKillboard 对，用户名变体（binkcn → Bink Wang）用 `npm run find` 试。
- 账号追踪同时核对展示名 `name_show`、原用户名 `name` 和 uid。展示名变成“贴吧用户_……”不等于没发帖；`hide_post=1` 只说明回复列表隐藏，转查主题、站内命中与他参与的帖。
- **楼中楼单独分页。** 主楼往往只带两条预览，按问题与预算读相关页；分页结束但数量不足仍记缺口。删除、折叠、计数滞后和限流都不当无料。
- **回查保存覆盖清单。** 抓取成功不代表人工已看，没读完不说读完。403/429 立即停止这一批并冷却，续跑不能跳过之前失败的条目。
- 原始输出可能含现实隐私，只放临时目录。

### 3. 搜索引擎

先 Google（代理自带网页搜索，加 `site:tieba.baidu.com`）和必应，最后才用百度/360（容易限流）：

- `node scripts/research/baidu-search.mjs "某某 eve欧服吧"`；按需选 `--so`（360）或 `--bing`，被拦不自动轮换。
- 批量：`node scripts/research/batch-search.mjs <清单.tsv> <输出目录>`，固定引擎、每轮最多 10 条，缓存跳过，遇拦截整批停止。

| 目的 | 关键词（“某某”换成中文名、外号、角色名） |
| --- | --- |
| 评价 | `某某 eve欧服吧`、`如何评价某某` |

### 4. B 站（与贴吧同等重要）

- **发现方向**：先用 `npm run materials -- "人物或账号名" --kind bilibili` 查正式档案，命中就复用 UID／BV，未命中在素材记“待板块扫描”。不按人名、外号或角色名搜 B站；素材已有确切 UP 名只缺 UID 时，可按该名用户搜索一次；本人简介、帖子等已对应账号贴出的链接直接读，读后补进 UID 档案。新增发现只走下方[B站扫描队列](#b站扫描队列)，汇总 UP、按 UID 去重登记后再反查人物；成功页与失败记录直接复用，不重扫。
- **战役视频候选**：选取按[内容规则](content-rules.md#战役)。先从本地档案按标题、投稿日与简介为交战各方分别找候选，不受下方关注度粗筛限制，低播放、低评论的小 UP 参战录像同样核读；不先按播放截取大 UP 再声称另一方没有作品。00 区史诗战役仍不足 2 个时的补搜见[工具细节](research-tools.md#少用的补查入口)。
- **战役视频关联**：综合作品主题、发布日期、完整简介、原作说明与 BR 判断，不只看标题；日期换算、近 5 日规则和简介 BR 与主报不同的处理按[来源对战役](#来源对战役时区与战报)。
- **简介战报入口**：读作品时查完整简介及旧版本里的 BR／KM／原作链接，随简介留在 UID 档案；用 `node scripts/bilibili-archive.mjs reports [偏移] [条数]` 离线查漏，输出只表示取得入口，不表示已核战报。清理联系方式时不连带删掉同一行的公开战报链接。
- **持久档案优先**：按查询结果读 UID 档案、`channel.prior_notes` 与作品 `reading.material_refs`，取得与消化分开记（流程和字段见[档案说明](bilibili/README.md)）。已存的频道与作品文字离线复用；缺精选、旧状态过期、换会话或缓存清理都不触发全频道重读，只定向补读实际缺失的作品。
- **图文必须单查**：调查已知 UP 时同查 `/upload/opus` 图文列表，不只记图文数量或只看视频排序。先复用档案中的图文覆盖、候选与 `posts[]`；列表按实际页次／滚动范围记录，单篇读正文、配图文字与相关作者回应，未加载、未翻页、未读图分别留缺口。重要事件、争议、复盘和已有故事的关联图文优先，不套关注度粗筛，没有计数不当零也不作跳过依据。图文与旧专栏归同一 UP JSON（见[档案说明](bilibili/README.md#图文与旧专栏)），事件摘要归原素材，不另建图文全员表。
- **先读空间，再定作品候选**：首次调查已对应 UP 或补精选时，先核空间简介、视频／图文数量、合集与系列；同一人物有多个已对应账号时逐个核，只在作品里被点名的候选账号不混作本人账号。分别看“最新发布”（近期活动）和“最多播放”（历年代表作），核对当前选中的排序并记实际页次，两者不互相替代；缓存须含排序和作品内容才可复用，未查最多播放不能把最新页的高播放说成全频道最高。按创作主线、重要事件与系列补候选，不只追最近发布，也不以补完频道为目标。
- **候选之后才读作品**：最新、最多播放、代表系列和已知事件的候选合并去重后，按预算读简介、选集、作者公开文字与评论。播放量只用来发现候选，不证明作品优秀；评论补作者故事、互动和争议，不替代空间调查，也不能凭热评评价画面、剪辑或讲解。默认读文字，不为找角色名逐段播长视频；转载视角和标题战损不直接归本人。合作作品另核公开创作团队与本人署名，owner 只说明上传者，不把合作独算本人，其中的具体事迹仍可归档、入文。跨平台对应按内容规则第 2 节。
- **精选怎么判**：选取规则见内容规则第 2 节“B站 UP 作品精选”，多个本人账号合并去重后总共最多 5 个。本人带队、实战记录、教学和系列创作本身就是看点，不要求另有社区事件、评论笑话、作者答疑或“本人制作”声明；已对应频道、角色简介自荐与本人系列的实战作品结合这些上下文判断归属，简介只写“视频已加速”或评论少都不是排除理由，外网链接也不一律算不合格。首批读取上限不是整项上限，好候选多时按批次补读。推荐语写已知主题、人物特色和适合谁看；未看视听不评操作、剪辑或画面。仅见标题／计数的只留候选；未读或受预算／访问限制的记未完成，不判成质量不足，内容依据不够就写精选待补。“B站”是身份标签，不作别名，清理别名不连带删标签。
- **关注度筛选**：暂用粗筛，播放不足 1000 且评论不足 10 的作品不主动续读，只留标题、出处和当时计数；一项明显受关注的仍可候选。先用已有计数筛，不先批读再剔除；评论数别拿空间卡片上的弹幕数顶替（见[工具细节](research-tools.md#b站网页读取)）。粗筛只用于安排未读作品，不代表质量或收录门槛。
- **先验证读取方式**：新增或修复评论读取方法时，先用一个有评论的页面核对实际评论正文与覆盖，再扩批；页面可读不等于评论已读。拿到一次空评论结果先查加载状态，不把同一失败方式批量套到剩余作品；懒加载与 shadow DOM 的坑见工具细节。
- **登录复用**：已授权读取 B站 Cookie。API 通过 `bilibili-session.mjs` 从可连接的 Chrome B站标签取会话，只在请求内存中使用，不存文件、不进日志或 Git，不读其他网站凭据。Chrome 沿用持久配置；日常窗口与独立窗口的登录状态可能不同。
- **失败处理**：API 遇 403／429／412／-352，停止该站 API 并冷却至少 30 分钟，不换接口或出口；这不等于 Chrome 网页也不可读。Chrome 遇验证或拦截也停止并单独冷却，不重置停止记录续跑。
- **覆盖边界**：等页面正常加载，不刷新加载壳。核对投稿总数、可见 BV 与页次；视频页最多取 20 个已加载主评论线程，不翻页、不展开楼中楼。合作账号注销也不代表视频失效。只把实际读到的内容记入素材，保留分页与身份缺口。

| 入口 | 命令与限额 |
| --- | --- |
| API | `node scripts/research/bilibili.mjs <命令>`：`user`、`search`、`videos <UID>`、`info <UID>`、`video <BV1,BV2,…> [评论页数]`、`dynamics <UID>`。每个关联UP／事件约15次请求，最多选5个有料视频批读；成功缓存位于 `.cache/bilibili/`。 |
| Chrome | `node scripts/research/bilibili-chrome-read.mjs <公开网址或清单.json> <.cache/输出目录> [最多页数]`。Windows Node≥22＋系统Chrome；清单为 `[{"url":"公开网址"}]`，支持投稿、视频、动态／专栏和搜索页。默认30页，单批上限60页；批量范围与总预算先写进唯一续查队列。 |

#### B站扫描队列

检索词、排序与页数只在此维护。只用 `EVE欧服`、`EVE`、`星战前夜`、`EVE国际服` 四词，按此顺序逐词独立搜索；每次只输入一个完整词，不拼接联盟、事件、舰船、招新等限定词，也不另设话题或组合词。

固定**综合排序**，每词读第 1—30 页，不足 30 页读到实际末页并记录；不切排序，不拿其他词或其他排序的首页代替后续页。按作者 UID 与已有档案去重，直接登记 `docs/bilibili/<UID>.json`，再对照列传、素材和备忘录反查人物；零星投稿的作者同样保留，不按出现次数缩小发现范围。

覆盖、失败、下一页与旧排除记录在 `docs/bilibili/scans.json`，用 `node scripts/bilibili-archive.mjs scans` 离线查询。旧记录称四词本轮已完成，但没留日期和各词末页：沿用该记录，不补造页次，不因迁移重扫；更早的组合词浅扫不算四词覆盖，也不续跑。开新一轮时记录每词实际页次、去重登记与下一页；遇 412／-352 整批停止记断点，不换词或排序绕过。

### 知乎（有料，别跳过）

知乎有当事人亲笔长答（本人解释被封、联盟史专栏）和“如何看待某某事件”的对线，贴吧没有的细节常在这里。按需用有头浏览器工具；遇验证码提示人工处理，最多等 10 分钟，无响应则停止，不自动换路径：

| 要做什么 | 命令 |
| --- | --- |
| 搜索（经搜狗知乎站内，知乎自带搜索未登录无结果） | `node scripts/research/zhihu.mjs search "关键词1" "关键词2" [页数]` |
| 读问题 / 文章与评论（预算内） | `node scripts/research/zhihu.mjs read <网址>...` |
| 列某人文章与回答（预算内） | `node scripts/research/zhihu.mjs user <主页或url_token>` |

- 宽泛关键词（“eve欧服”）九成是萌新问答，还费验证码；搜事件词和人名：`eve FRT`、`如何看待 某联盟`、`某某 eve`。标题含“如何看待/如何评价”加事件的优先读。
- 评论区常有本人现身回复；“知乎用户”匿名答主可凭评论区署名或内容认人。

### 外网（外国联盟、华人被老外爆料的戏多在这里）

- **Reddit（r/Eve）**：reddit.com 网页和 `.json` 都被拦，代理自带网页搜索也几乎搜不到具体帖。读帖一律用 `node scripts/research/reddit-thread.mjs <帖子ID或网址> <临时.json>`：走 pullpush.io 存档，打印正文和已取得的评论（评论编号 ← 上级编号、作者、日期），未完分页留缺口，原始数据存临时文件。
  - 按关键词找帖：`node scripts/research/reddit-search.mjs "\"Army of Mango\"" [posts|comments] [subreddit=Eve] [条数]`（同走 pullpush）。找不到帖子时，先找引用过 r/Eve 的英文二手文章（Talking in Stations 节目页、tagn.wordpress.com、imperium.news、New Eden Post），其链接列表常给出原帖编号。
  - **限流**：pullpush 对密集请求回 429（并声明不给代理免费抓取），Wayback 也会 429。脚本遇 429 立即退出；有新需要才评估恢复，不循环重试、不换站硬刷。
  - 存档接口一次最多回 100 条评论，脚本在预算内翻页；单次响应不是全文，曾因此漏掉三分之二评论，包括认出当事人的那条。
  - 网址里 `?c=…` 这类分享参数不是评论编号，直接读全帖。
  - 截图只有 `preview.redd.it` 链接，存档不描述图片内容，需要时另行下载。
  - 涉及华人的帖，评论区常贴贴吧或 B 站链接，顺着去读；爆料人把军团介绍、联系方式昵称和角色名对起来的评论最有用。
  - 帖中角色名常有出入（缺前缀、拼写差一点）：ESI `POST /universe/ids/` 查名字，再看相关军团的 `ceo_id`、`creator_id`，用 `npm run find` 确认。
- **官方论坛**：forums.eveonline.com 的 `search.json?q=关键词`，多试几组英文关键词（人名、联盟名、事件词）。
- **凛冬论坛**（forums.winterco.org，有 `.json` 接口）：常有 r/Eve 戏的中文转述。
- **帖中链接的 Google Docs**：`/export?format=txt` 取全文。
- 结论按实际覆盖表述；未查渠道或被拦入口写缺口，不为证明“查不到”反复查询。

## 三、原帖读不到时

- 网页被拦：记录失败并停止，有具体新需要时再选其他公开来源。
- 帖子被删：Google 搜标题和帖子号，查 Wayback `https://web.archive.org/web/<时间戳>id_/https://tieba.baidu.com/p/<帖子ID>`、archive.is。
- 只有搜索摘要也能当来源，素材注明出处是摘要；不因读不到全文就放弃。

## 四、发现新人物

按名字找只能找回已知的人。改以社区帖子、回帖和作者网络为主线，名册作补充；一条入口的零结果不能代替另一条：

1. **社区故事发现人物**：给贴吧帖子列表的“标题 + 首楼”打分：职务词（总监、CEO、团长）、冲突词（弹劾、背刺、澄清、骗、跑路、封号、悬赏）、叙事词（前传、始末、回忆、经历）加分，招新、交易、求助减分。叙事分与回复量是两条独立入口：高回复帖不因标题普通、招新、求助或首楼无冲突词而淘汰，回复量前列的中性帖单独排队，至少读首尾和楼中楼再决定是否读全文；数字加物品或事件词的标题也抽样读。同一吧、同一批的相对排名优先于固定阈值。
2. **按楼主 uid 聚合、追被点名者**：短期连发长帖、连开十来帖的楼主本身可能就是名人；回帖多但只开过一帖的人也可能是关键人物，不能只按主题数筛。楼中反复出现的人名、`@`、别名和“这位就是……”“又是他”都转为候选并查重；角色藏在回复里时，不因标题和楼主不是他就跳过。用 uid 合并改名账号，保留原用户名和展示名。
3. 排除已读帖子号再看。列表接口只回溯到约 2024 年中，更早的用站内搜索加上述关键词。
4. **名册补充**：CSM 候选、锦标赛队伍、军团管理名单等名册可补漏，做法见[工具细节](research-tools.md#少用的补查入口)；发现人后仍回社区帖子找故事。
5. **联盟执行军团**：华人联盟还要查 ESI `executor_corporation_id` 对应的执行军团，优先逐个追现役角色的公开头衔、职责和社区事件，同人小号并回原人物。先复用现役名册、历史 CEO 和军团榜单，但后两者不能代替现役名单。每轮首批最多十人，记任期、覆盖与未查项。

收录按内容规则第 2 节：有自己独立人物事件的（不只是别人回忆里路过一句）登记或立传；身份未对上才进 `docs/leads/` 与角色备忘录；只有简介幽默、自嘲、普通聊天、旗舰战果签名、KM 收藏和 KB 分析的，先存素材、身份与来源，再追具体事件。

## 五、已知的坑

- 角色名以本人或当事联盟写法为准；同一外号可能指不同人，用游戏数据或原帖区分。
- 找到收录号不等于找全本人；小号按第六节有需要时补查，先看已有覆盖，不等别人逐个报号，也不以 KB 名字检索没出现为完成依据。
- B 站视频被删且认不出作者时不引用。
- **低可信来源**：声望哥（小♂凯／Sirses／Wibrik2021）与咪咪（彭铁柱／koko1 k）同档。他们对别人的指控、定性和自报数字可以入料，但正文写成本人一面之词，笑点落在发帖人身上；不单凭其说法给第三人定黑料、职务或标签，有他人独立说法时以他人说法为主线。他们发帖、点名、悬赏等本人行为照常算本人的料。

## 六、小号查漏（有需要才补查）

沿已有身份线索选用以下入口，不当每次修订的必跑清单；统一遵守联网条件与预算。

- **名字扩查**：从角色名、aliases 拆词根，查编号、大小写／形近字及用途前后缀。明确系列才用 ESI `POST /universe/ids/` 有限批量补查，不默认穷举编号。
- **EveWho 前缀搜索**：`/autocomplete/<小写且 URL 编码的词根>`，取 `suggestions` 中 `data.type == character`。每类最多 10 项，满额记截断，只在预算内拆有线索的分支；不做错拼容错。接口见[公开源码](https://github.com/zKillboard/evewho/blob/master/www/controllers/autocomplete.js)。KB 自动补全可能漏掉无击杀的号。
- **军团榜单反查**：从当前或相关历史军团的高 KM 榜选少量候选，读头衔和完整简介，与全站中文名、别名及素材对照，可能找到英文名不同的小号甚至主号。用 `api/stats/corporationID/<ID>/` 的 `topAllTime` 角色榜，别把近期 `topLists` 或有限榜单当全体成员。
- **月份口径**：`/corporation/<ID>/top/` 默认当前月，`/top/year/<Y>/month/<M>/` 取指定月；`topAllTime` 不替代月榜，未标日期的 `topLists` 不推断为最近完整月。先看返回字段与数据类型，再记实际窗口、榜长、取得状态和已核身份；请求失败只留缺口。
- **身份核对**：结合自报头衔、角色互链、相近名字与当前／历史同军团、时间重合判断；同批建号、同步入退团可加固对应，只有“FC”等常见头衔或同联盟不足以合并。退团不抹掉已建立的同人关系。
- **补录**：同人的名字、ID、对应依据与来源按内容规则第 2 节写入身份档案与本人素材；发现主号时记择号依据。未对上、未查和失败分别留缺口，不另立小号传。

## 七、监视者驾驶员反查

华人联盟或军团的 Monitor 驾驶员是高优先级 FC 主小号线索，主动从已取得的战报、KM 和船型榜查漏，不只查被点名者。按战时归属筛选；联盟有外语成员时继续核对军团、头衔与中文社区交集，不把整个阵营当华人个人。

先对照收录号、aliases 与素材中的历史小号，再查公开中文头衔、简介、同词根及当前／历史军团。明确对应的并入原人物；有独立故事且角色对得上的直接立传；未对应的在 `docs/leads` 备案并登记 pending-characters，至少写角色 ID、代表 KM、时间、战时军团／联盟、已查项和缺口。监视者说明参与指挥，不直接证明总指挥，也不能单凭同船型或同联盟合并真人。复用共享样本，遵守统一预算；高值抽样未命中不当作没有驾驶记录，未全扫的说明范围。按军团／联盟查驾驶员用下文高级搜索：攻击方栏放军团或联盟加 Monitor，选 In。

### 系统 Chrome 月榜读取

有明确浏览器读取需要时用已连接的浏览器工具；需要脚本保存正文、表格、角色 ID 及击杀链接时，运行 `node scripts/research/chrome-read.mjs <zkillboard网址> <.cache/输出前缀>`。月榜后加 `ship/45534/` 可查 Monitor，先核 Top Ships 确实只剩 Monitor。KM 的“List all pilots”展开后才是完整参战名单。导航计预算，验证未通过则停止并留缺口，打开窗口不等于取得数据。

### zKillboard 高级搜索（asearch）

stats 回答不了、又确实需要 KM 名单时才用，例如“某军团谁开过 Monitor”，或为某个说法找几张代表 KM；只问“多不多”先看 stats。一个问题一条精确筛选，默认 `--ids-only` 或 `--details` 十张以内；不按年、月、船型、小号循环跑，不全量补全：

`node scripts/research/zkill-asearch.mjs <asearch网址或#后的JSON> <.cache/输出前缀> [--details N] [--ids-only]`

脚本把 `#` 后的筛选条件译成查询参数，在独立 Chrome 里分页取全部击杀 ID（浏览器只用来过 Cloudflare），再用 zKB API 与 ESI 补全最新 N 张（默认 100），输出 `.json` 与 `.tsv`。tsv 的 `focus_side_ships` 列记录筛选点名者在每张 KM 上的身份与船型，用来核对查到的是不是想要的；提示“没找到筛选点名的参与者”时先查筛选写法。

**先想清楚要回答的问题，再写精确筛选。** 下面的写法和例子帮助理解工具，不是固定配方：只放回答问题必需的条件，不相干的条件（如查强暴时限定攻击方船型）会漏掉真实记录。服务器每页 100 张、最多 10 页；时间段满额时脚本对半拆段重查，这只是兜底——命中成百上千、要拆段，通常说明筛选写宽了。**零结果先用一个已知会命中的同类筛选对照**（同一人换一条常开的船），服务器超时也会回空列表。筛选 JSON 写法：

- **栏位**：`attackers`（攻击方）、`neutrals`（网页上的 Either，任一方）、`victims`（受害者）、`items`（掉落物品）。每项写 `{"type":…,"id":…}`，type 用 `characterID`、`corporationID`、`allianceID`、`shipID`（船型）、`groupID`（舰船分组）、`systemID`、`regionID`。
- **连接方式**（`buttons` 里的 `<栏位>-and`／`-aand`／`-or`，Either 栏写 `either-…`）：And 是每项各自匹配任意一名参与者；Or 是任一项匹配；**In（`aand`）要求同一名参与者同时满足全部项**。“某人开某船”必须把角色和船型放进同一栏并选 In；角色放攻击方、船型放 Either，查到的是“他在场且有人开这船”，舰队战里会混进大量别人开的船。
- **标签**（`buttons` 里写 `label-<标签>`；同组任一，跨组同时满足）：`ganked`（高安强暴：攻击方随后在同星系被 CONCORD 击毁；不含太空舱、战争、awox 与 100 万 ISK 以下，且只标 2018 年 2 月底以后的 KM，更早的强暴改用 `loc:highsec` 加时段另查）、`awox`、`solo`、`#:1`／`#:2+`…`#:1000+`（参与人数）、`loc:highsec`／`lowsec`／`nullsec`／`w-space`、`isk:1b+`／`10b+`／`100b+`／`1t+`、`capital`／`super`／`titan`／`capinv`（有旗舰参与）、`tz:au`、`cat:6`（只看舰船）、`pvp`、`npc`。
- **时间**：`buttons` 含 `custom` 并写 `dtstart`、`dtend`（UTC，`2020-01-01T00:00`）；全时段写 `alltime`。排序 `sort-date`、`sort-desc`。
- `victimsonly`／`attackersonly` 按钮与 `includeAssociates` 只影响网页侧栏的排行汇总，不改变击杀列表。
- 船型等 ID 用 ESI `POST /universe/ids/` 或 `/universe/names/` 核对，不凭记忆写。

例：

```text
某人开 Monitor 的全部 KM
{"buttons":["alltime","attackers-aand","sort-date","sort-desc"],"attackers":[{"type":"characterID","id":<角色ID>},{"type":"shipID","id":45534}]}
某人参与的高安强暴（不限攻击方船型）
{"buttons":["alltime","label-ganked","sort-date","sort-desc"],"attackers":[{"type":"characterID","id":<角色ID>}]}
某联盟谁开过 Monitor（tsv 的 focus_side_ships 即驾驶员名单）
{"buttons":["alltime","attackers-aand","sort-date","sort-desc"],"attackers":[{"type":"allianceID","id":<联盟ID>},{"type":"shipID","id":45534}]}
```

一次脚本运行计 1 次 zKillboard 搜索。拿到的 KM 与驾驶员仍按本手册其他规则核对身份、归属与红黑分类；KM 上有名字只说明参与。
