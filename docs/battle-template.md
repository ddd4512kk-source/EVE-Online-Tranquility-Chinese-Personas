# 战役文件模板

每场目录 `src/battles/<短名>/` 只维护一份同名 `<短名>.json`，以及正文 `<短名>.md`、素材 `materials-<短名>.md`。Markdown 不写 front matter；配置与快照放在同一 JSON 的两个字段，不再另建 `battle.json`、`br.json`，不在两处重复组织名单。

## 同名 JSON

```json
{
  "battle": {
    "title": "回目式标题，抓本场最有戏的一点",
    "aliases": ["别名一", "别名二"],
    "epithet": "一句话锐评，不超过二十五字。",
    "start": "2026-10-10",
    "systems": ["Obe"],
    "tags": ["低安", "超旗战"],
    "sides": [
      {
        "name": "甲方及友军",
        "organizations": [99003581, 1727758877],
        "emblem": 99003581
      },
      {
        "name": "乙方及友军",
        "organizations": [99004901],
        "emblem": 99004901
      }
    ],
    "loss_source": "https://br.evetools.org/related/30002086/202305141500"
  },
  "br": null
}
```

上面是字段结构示例，来源、日期、星系及组织须替换成本场实际记录，不能直接把示例当成战役。新建时 `br` 可以先为 `null`，运行 `npm run fetch` 抓取后填入；快照缺失或过期时离线校验会报错。手填战役的 `br` 保持 `null`。

- `battle`：人工维护的战役配置。刷新时保留这一整块，不重写已经核对的分方、战徽或其他字段。
- `br`：抓取来源战报后精简的快照，勿手改。角色、军团与历史联盟、损失记录、原始分队和交火信息保存在这里，计算结果不重复写回配置。
- JSON 顶层只允许 `battle` 与 `br`。修改来源、星系或时间窗时，fetch／build 重新取快照，只替换 `br`。读取与写回都由统一档案入口完成。

## battle 字段

- `title` 必填，野史回目式标题；标题中的低安星系使用已登记中文名，英文名保留在 `systems`、`aliases`。命名依据留素材。
- `aliases` 可选，别名列表；`epithet` 可选，一句话锐评；`tags` 必填，恰好一个地带和一个战斗类型，分类与自动标签见下节。
- `start` 必填、`end` 可选，UTC 日期，格式 `YYYY-MM-DD`，跨日才加 `end`；`systems` 必填，游戏内星系英文名列表。
- `sides` 必填，2–4 方，顺序决定页面阵营顺序；每方必填 `name`。归方依据、完整组织映射、来源冲突及采用理由存本场素材。
- `sides[].organizations` 是唯一人工组织归方名单，填写联盟或军团 ID。无联盟军团可以直接登记；有联盟的军团须与本场历史所属联盟同方，不得用军团点名覆盖联盟拆到对面。跨方不可重复，同方也不要重复；点名 ID 须在本场战报出现。没有点名的组织仍可从原始分队或后备推断得到归方，不能拿自动结果代替人工核对。
- `sides[].emblem` 可选，单个组织 ID，须属于该方 `organizations`；只负责战徽，不是第二份归方名单。不写时用阵营文字退路，不擅自挑选图标。
- `sides[].note` 可选，一句话补充，例如“折损泰坦130条”。
- `loss_source` 必填，总损失口径来源的完整网址；编组或多来源写网址列表。全是 br.evetools／killmail.app 战报时走快照统计，其他来源走手填。
- `window` 快照战役可选，UTC 起止时刻，如 `["2020-10-06 02:59", "2020-10-07 06:00"]`；只算窗口内击杀。手填战役不写此项。
- `loss_is_lower_bound` 可选布尔值，仅在确认是损失下限时写 `true`；目录与详情显示“至少”，按该下限分档，范围与来源留素材。
- `pilots_peak` 可选，同一时刻同一星系的最高同屏人数，不充作全程去重人数。
- 规模按各方总损失：100–不足400B为中型，400–不足1000B为大型，1000B及以上为史诗；不足100B构建失败。
- 只允许登记的字段，拼错、多写或把旧 `alliances` 数组留在配置里都会报错。名称统一取 `src/_data/entityNames.json`，不在战役 JSON 再抄一份名字。

## 战役标签

创建、分类与清理标准统一见[战役规则的战役标签](rules-battle.md#战役标签)。`battle.tags` 只存一个地带和一个战斗类型，例如 `["低安", "超旗战"]`；规模与完整参战联盟由构建生成，目录与详情共用，不在配置重复维护。战斗类型依据保留在本场素材。

## 快照归方与统计

先按战役规则实际阅读 BR 网页的完整分队，再与复盘、逐舰记录及本场已确认关系交叉核对。BR 并非绝对准确，不盲从默认 related，也不能完全跳过 BR。API 没有 `teams` 不代表网页没分队；人工核对结果记入 `battle.sides[].organizations`，依据留素材。

快照按点名组织把原战报队伍归方：同一队里点名组织都在同一方时，队友跟随；点名到“第三方”只摘出该组织，不牵动其他队友。没有分队、或点名分属多方时，未点名组织才进入交火推断后备路径。达到与两方交火至少3次、三分之二以上冲着一方的阈值时可推至对面；推断不是独立的外交或第三方证据，仍须人工复核。组织对各方旗舰（无畏、航母及以上）造成的伤害是最准的归方依据；平时先用战报分队只因省事，战报或 zKill 分队与旗舰伤害冲突时，以旗舰伤害为准。KM 署名次数与交火次数只算佐证，大量低伤害署名不能定方。没有现成战报时，自行生成 zKill related 窗口或用逐日 KM 存档核算，不等他人代点。

全场与各方人数、损失、KM数，华人军团人数及已收录人物由 `br` 计算，快照战役不手填数字、`corps` 或 `people`。人物错方时修正组织归方，小号通过本人档案 `identity.alts` 对应收录号，不在战役重复登记人物。未归组记录进入“第三方”；第三方不足30人时不展示，不写独立正文，不计显示方数，底层记录、全场统计与人物关联仍保留。

## 手填战役

没有逐角色快照时，`br` 保持 `null`，在 `battle` 里登记来源给出的数字，不从军团当前归属回填历史：

- `total_loss` 必填，全场各方总损失，单位B（6.64T写6640）。只有KM求和时标记已核下限。
- `pilots` 可选，全场角色数；不写且各方人数齐全时自动相加。
- 每方 `pilots`、`loss`、`loss_count` 必填，分别是参战角色数、按受害方计的损失B、按KM ID去重的损失记录条数。记录可含太空舱和建筑，不等于纯船体数。
- 数字确实取不到才写 `null`，并填 `stats_note` 说明来源缺口和续查入口；已确认零损失才写0，不能用全场数顶替分方数。
- 每方 `corps` 可选，华人军团项为 `{ "id": 98190062, "pilots": 20 }`；来源确认的历史所属联盟可加 `alliance_id`，0表示确认无联盟，未知就省略。
- 每方 `people` 手列参战的已收录人物收录号，一人只能出现在一方，人物页自动反链。正文用 `/p/<ID>/` 链到的人、列传正文链到的战役页，也会自动互链，不必为反链补 `people`。
- 联盟和军团仍使用统一的 `organizations` 名单，战徽使用 `emblem`，不恢复第二份数组。

## Markdown 正文

正文文件不写 front matter，按[战役规则](rules-battle.md#叙事与高潮)写成一条时间线：小节标题自拟，点出阶段而不是阵营；各方华人人物与军团随事件出场；最精彩的 2–3 个场面放进 `::: 高潮 标题` 块，留在它发生的位置；文末 `::: 评` 锐评。不念自动生成的名单，不再新写 `::: 红料`／`::: 黑料`。提到人物用 `[名字](../../p/<角色ID>/)`，提到别场用 `[战役名](../<短名>/)`；人物列传引用本场时用 `[战役名](../../battles/<短名>/)`，KM链接保留，不使用根路径链接。

下面是虚构示例，人物、军团与事件都是占位，只示范篇幅和写法：每节都有一个带人物、动作和结果的场面，数字只在推动情节时出现。

```markdown
（开篇）这一仗起于一句群聊里的狠话。[老周](../../p/<角色ID>/)的军团在某低安星系蹲了半年矿，被对面的海盗联盟连着拆了三座星城，老周在群里放话“下次谁再来，泰坦陪他一起沉”。对面当真来了，老周也当真把泰坦开了出去，于是一场本该是邻里拌嘴的仗，最后成了两边超旗一起进场。

## 一句狠话

起因写谁先动的手、为了什么，从华人这边讲。老周放话之后，军团里的骨干连夜……（展开成一个完整场面，四五句以上。）

## 拉人凑船

集结写谁去摇人、谁带队、谁临阵换边。外国盟友只作背景，镜头跟着华人走……

## 桥开在了对面脸上

交锋写战线怎么推进，各方华人人物在其中做了什么。没有专门料的参战人物，按身份写一段过场……

::: 高潮 三十秒的超旗墙
一个完整场面：谁在什么局面下做了什么、怎么翻的、各方什么反应，再一两句损。块内不重讲背景。
:::

## 收拾残骸

转折与收场写局面在哪一刻翻过来、各方怎么收场、事后谁在群里说了什么。

::: 评
文末锐评，一两段即可。
:::
```

## 命名与取数补充

- 标题用有戏的野史回目，抓本场最出名的反差或笑柄，不套“某某之战／战役”；已有响亮社区叫法就沿用。平实地名、英文名放 `aliases`，起名依据记素材。短名用 `<星系或通称>-<年份>`，如 `obe-2026`。低安中文名与编组规则见 [战役规则](rules-battle.md#收录与统计)。
- br.evetools 支持 `br/<ID>` 与 `related/<星系ID>/<时间>`，killmail.app 支持 `br/<ID>`。两家同场战报可合用，KM 按 ID 去重，分队取有分队的那份；修改来源、星系或窗口后 fetch／build 自动重抓。
- 点名联盟前按战役规则与[战役取材](research-battle.md#发现战役与读战报)读完网页全部分队。点名与原分队冲突会触发后备推断，须复核未点名组织的去向，不能把自己点名冲突的结果反过来当成BR分组错误的证据；军团点名与本场历史所属联盟必须同方，冲突须修正映射。联盟名会重用，按本场 ID 认组织。
- 手填统计无现成汇总时，同一窗口与星系内按 KM ID 去重；人数取本方攻击者与受害者角色 ID 并集，损失按受害方计。逐张比对人物落方，归不了方的留素材。
- 战役正文取指挥、动员、名场面、重大损失、阵前跳槽等事件排成时间线，最重的进高潮块；个人船型及逐号统计留在本人列传与素材，不念自动生成的参战名单。

## 相关视频填写

在同名 JSON 的 `battle` 增加 `videos`，页首统计下方自动生成“相关视频”。不填写或填 `[]` 时不显示。收录与署名要求见 [战役规则](rules-battle.md#收录与统计)。

```json
"videos": [
  {
    "title": "作品原题",
    "url": "https://www.bilibili.com/video/BV1UK4y1H7XT/",
    "author": "UP主名称（联合制作可补公开署名）",
    "description": "简短说明作品与本场的关系及值得关注的内容。"
  }
]
```

战役关联按[战役取材](research-battle.md#来源对战役时区与战报)判断；选取按战役规则，全页最多 8 个。

使用 HTTPS 的完整 BV 链接或 `https://www.youtube.com/watch?v=<视频ID>`，不填短链、播放器地址或空间主页；同一视频只留一次。YouTube 条目的 `author` 填频道名。链接指向原站，不内嵌播放器或加载外部封面。

## 战役头图

有视频的战役挑一个封面作头图，在 `battle` 增加 `"cover": "videos 中的网址"`，再运行 `npm run covers -- <短名>`，自动居中裁成 16:9。优先选画面好看、能看出本场战况的游戏截图，避开现实人物和与本场无关的封面；没有合适封面就不写，头图退回对阵横幅。

封面带原作者的大字标题时不放弃整张图，按下面的标准流程改成自己的标题：

1. 看原图（1920×1080 一类原始像素），量出大字所在矩形，填进 `coverEdit.erase`，格式 `[x, y, 宽, 高]`，可多块。脚本把矩形内的亮色字迹连同描边抹掉，用周围背景填平。
2. 在 `coverEdit.lines` 写自己的标题，每行 `{ "text": "…", "size": 字号, "x": 左边距, "y": 基线 }`，最多 4 行，白字黑描边；放在抹字的位置，避开战场主体、人像和界面重点。
3. **图内文字不得与页面文字重复**：不能等于或包含本页标题、副标题（校验会拦）。图上写页面没说的另一个钩子，例如一个人物的外号、一个反常细节或一句场面，内容仍须有出处，与正文口径一致，不写未核的数字。
4. 运行 `npm run covers -- <短名>`，打开生成的 `cover-<短名>.webp` 目视核对：字迹抹净、无色块和竖纹、新字不压住战场；再跑校验与构建。

```json
"cover": "https://www.bilibili.com/video/BV1UK4y1H7XT/",
"coverEdit": {
  "erase": [[20, 270, 520, 250]],
  "lines": [
    { "text": "大字钩子", "size": 96, "x": 40, "y": 395 },
    { "text": "一行补充说明", "size": 44, "x": 40, "y": 470 }
  ]
}
```

原封面没有大字时不写 `coverEdit`，也可以只写 `lines` 给无字封面加标题。


## 自动联盟参与

快照统计同时产出 `alliance_participation`（每方联盟ID、角色数、损失B、KM数、实际军团ID列表）与 `corporation_affiliations`（军团ID及本场出现过的联盟ID；0为无联盟）。一份本场快照是这些结果的唯一历史归属依据，编组与当前名称表不提供历史归属。军团可能在同一轮记录中出现多个联盟ID，分别保留，不用现今归属覆盖。

页面与目录的联盟列表来自该计算结果，只列本方至少10个参战角色或本方有华人军团所属的联盟，按角色数、损失排序；不足10人且无华人军团的联盟不进阵营名单；联盟标签另按本方参战角色占比30%的标准取舍，与名单门槛分开；`emblemOrganization`只保留`emblem`选定的主标，与完整参战名单分开。本场已登记归方且无联盟的独立玩家军团同样按至少10个角色或华人军团条件展示，人数与损失由`independent_participation`保留；NPC军团不作为独立舰队展示，不因出现在人工归方名单就把散人列成主要组织。小规模第三方整体展示规则不变。名称和缩写通过构建补缺，构建补名覆盖标签所需的全部历史参战联盟，不能只检查手写点名或达到阵营名单门槛的联盟。快照已证明是联盟、但名称尚未缓存时，显示“联盟 #ID”并报告缺口；查询服务维护时保留记录，稍后抓取补齐。手工归方种子的 ID 仍须通过严格名称校验。运行 `npm run audit:battle-participation` 可输出所有战役的联盟统计、所属军团和缺名 ID，供回查，不需逐页手算。

手填战役不具备逐角色快照时，军团可写 `{ id: 98190062, pilots: 20, alliance_id: 1354830081 }`；该历史联盟须有本场来源，`alliance_id: 0`表示确认当时无联盟，不知道就省略。历史联盟自动加入该方联盟列表，不手算重复人数或把当前联盟写回历史。精确联盟人数仍须有来源，不从单一军团覆盖率反推联盟全体。
